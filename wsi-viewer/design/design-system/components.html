View
Every element marked data-live is driven by the engine in the product; everything else is static chrome. Case, slide and patient content is synthetic.

How to read this sheet

Each component is authored once and rendered twice: in the dark diagnostic theme (the only theme permitted on diagnostic surfaces) and in the light chrome theme (an opt-in for Stoipath Learn and non-diagnostic Viewer sessions). The canvas backdrop stays neutral dark grey in both. Each section lists what the engine renders versus what the DOM renders, which plan contract the component consumes, and its ARIA and keyboard behaviour. State columns use the .is-hover, .is-focus, .is-active and .is-disabled classes, which mirror the real pseudo-classes so the states can be reviewed without a pointer.

Tokens: colour, type, space

Everything below is a CSS custom property in tokens.css. Surfaces and text are sRGB greys with OKLCH chroma 0; the accent and the four semantic colours exist but are confined to the dialog layer (modals, sheets, command palette), because the top bar, rail, dock and strip all sit within 32 CSS px of tissue (principle P7, Design note D14). Contrast and chroma are validated by contrast-check.py; results are in README.md.

App frame: the six regions

One fixed CSS grid: A top bar · B canvas · C tool rail · D context dock · E status strip · F navigator. Track sizes come from --layout-* tokens and never depend on canvas content, so a panel re-render cannot re-lay out the canvas (P2). The chrome collapses in the order fixed by principles §7 as the viewport narrows; the canvas never collapses. Resize this window to see the breakpoints: dock → drawer below 1600 px, rail → bottom bar and dock → sheet below 1080 px, strip hidden and navigator behind O below 600 px.

ARIA, keyboard and layout notes
  • Document order equals visual order: skip link → top bar (badge → label → identity → mode → overflow) → canvas (role="application", tabindex="0", labelled with slide, magnification and the pan/zoom keys) → rail → dock → strip → navigator. Two live regions sit at the end of the DOM: polite (position, magnification, sharpness; one announcement per 500 ms, at settle) and assertive (identity mismatch, Dx dropped, session expired).
  • Inside the focused canvas only unmodified keys and Shift-combinations are bound; Tab always leaves the canvas; Esc cancels the tool. Shortcuts work whenever the window has focus; the focus ring says where keys will land (QuPath/OpenSeadragon focus bug avoided).
  • Variants: .app--embedded (EHR iframe: 40 px bar, 24 px strip, no rail or dock, hand-off button), .app--widget (Jupyter: 36 px bar). .dock-open, .nav-open, .rail-closed toggle regions between gestures only; .is-gesturing zeroes every transition.
  • The dock resizer is keyboard-operable (←/→ in 16 px steps, 320–520 px); the navigator's pan buttons are the SC 2.5.7 drag alternative and appear on hover/focus.
  • The central 50 % × 50 % guide (toggle above) must contain nothing but tissue and the user's own annotations at rest.

Top bar: product badge, label string, mode indicator

The build and the render mode must be readable from any screenshot (P4). The badge sits in a fixed-width slot at the far left that no title truncation can push off screen; the full label string is visible without interaction at ≥ 1024 px and one tap away below; the mode indicator is the right-most fixed element in Dx-capable builds and is absent in Viewer and Learn. All four badges are neutral luminance steps plus text, because the 48 px bar lies within the 32 px tissue margin; Dx is told apart by text, the check glyph and a double rule. Modals and toasts are inset so they never cover these three slots.

ARIA, keyboard and labelling notes
  • The badge is a <button> whose aria-label carries the full product name and the label string, so a screen-reader user hears the claim without opening About. Activating it opens the About sheet (UDI, version, build_hash, pathway_hash, telemetry switch, complaint intake in Dx).
  • Below 1024 px the label string is hidden visually but remains in the badge's aria-label; it is also shown in full on the launch interstitial and on snapshot footers (burn-in by the engine).
  • Tier 1 is never shown. Tier 2 shows a chip only when it limits a mode (Tier 2 · 60 Hz / Tier 2 · reduced memory); Tier 3 always shows Tier 3 · best effort. The chip opens a sheet with the plan's bounded promise.
  • The worklist chip reflects the LIS-passed state and is never editable here (the viewer does not own the worklist). Shape + text carry the state: ring = ready, filled = in review, check = reviewed.
  • Learn builds never show accession, label image or patient fields (no PHI by construction); the identity slot carries module title and stepper instead.

Status strip: sharpness, Rendering Complete, network, offline, tier

The strip is the visual twin of the polite live region. It is 28–32 px, text only, entirely neutral (it touches the canvas). The sharpness indicator is a single glyph plus a short label driven by the quality record; it never uses red or green and only speaks when the pixels are not what they look like. In Dx mode it is replaced by one of exactly three Rendering Complete strings set by the Class C verifier's flag.

ARIA, timing and honesty notes
  • The indicator is a <button> (opens the quality sheet: NTF %, deficit in octaves, upload age, link estimate). Its text is mirrored verbatim into the polite live region at settle, debounced to one announcement per 500 ms; no second wording exists.
  • Sharp is shown only when the settled frame has NTF % = 0 and resolution deficit ≤ 0.15 octave (NFR-P16); the label fades after 800 ms (--hud-label-fade-delay), the glyph stays. Soft appears after 400 ms settled with deficit > 0.15 and always names a reason.
  • Glyph grammar: filled dot = sharp, ring = in progress, half dot = soft, slashed ring = offline, check = Rendering Complete, square with "!" = Not complete. Luminance and shape only; no red/green.
  • In Dx mode the strip never shows the Nav sharpness vocabulary; DX in the top bar is never shown without one of the three Rendering Complete strings here.
  • On phones the strip is hidden and the sharpness dot joins the HUD (.hud__sharp); notices move to a sheet.

ARIA and keyboard notes
  • Native <button> always; icon-only buttons carry aria-label and a tooltip with the shortcut. Disabled uses the disabled attribute (removed from tab order) except for toolbar tools that must stay discoverable, which use aria-disabled="true" and announce why.
  • The shortcut shown in a <kbd> is read as part of the name ("Bookmark, B"); shortcuts are rebindable, so the hint is rendered from the command registry, never hard-coded.

  • Destructive actions in the dock use .btn--secondary with explicit text; the coloured .btn--danger lives in confirmation dialogs.
