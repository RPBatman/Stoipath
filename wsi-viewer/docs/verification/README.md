# Claims-verification report — Stoipath WSI viewer plan

Date: 2026-10-25. Inputs: `verify/claims.json` (24 load-bearing claims extracted from `arch/recommended.md` and the research corpus), `verify/verdicts.json` (per-claim verdicts from three independent lenses: first-principles arithmetic, primary sources, on-this-machine experiments; plus a computed overall status), experiment artifacts under `verify/artifacts/`, `verify/ps-*/`, `verify/lens-*/`. Companion file for the section revisers: `verify/required-changes.json` (24 entries, one per claim, keyed to plan section files). Machine for all experiments: 4-vCPU x86 Xeon 2.1 GHz container, 15 GB RAM, Node 22.22, Chromium 153.0.8010.12 (Playwright, ANGLE/SwiftShader Vulkan, no display), Rust 1.97 stable, libjpeg-turbo 3.2.0; the box was shared with other agents (load average 5-18 on 4 cores during every timing run, recorded per result file), so CPU-side timings are upper bounds and bandwidth-shaped timings are robust. No phone, tablet, GPU, photodiode or radio was available; those items are listed in §4.

## 1. Summary

Of 24 claims, **4 are supported** (C03 WebKit 60 Hz cap, C08 texture-array arithmetic, C16 GPU-API reach, C18 no shared memory on the web), **16 are adjusted** (the fact or number is right in kind but a value, unit, baseline or scope must change), **4 are contested** (lenses disagree and the report resolves them below: C02, C06, C10, C23), **0 refuted**, **0 inconclusive overall** (six individual lens verdicts were inconclusive because the claim is not testable on this machine, chiefly C02 native floors, C15 radio inputs, C20 desktop overlay, C23 perception). No finding overturns the architecture (Rust/wasm core, web-sys WebGL2 floor renderer, WebGPU/wgpu upper tier, native shells at month 12, Edge Translator over a canonical store, OSD as comparator) and the relative gates (warm I2P ≤ REF + 1 frame; REF-quad + 1 interval) survive intact. The four findings that most affect the plan are:

1. **The web warm input-to-photon rows are about one 60 Hz frame optimistic and the wheel path is two.** The 40/50 and 45/55 ms rows are floor-configuration sums (2 present vsyncs, pointer input with a pending rAF); a stage model and Chromium's own pipeline docs put typical web warm I2P at ≈48/61 ms desktop-class and ≈55-65/70-78 ms on W-4G/W-iPad, and EventLatency traces show Chromium delivers non-passive wheel input rAF-aligned (16 ms p50), so wheel zoom is ≈60 ms p50 (C01). The native-shell case does not shrink: the corrected web→native iPad gain is ≈25-35 ms, not 20 (C01/C02), but the N-iPad 'typical' may be 33/42 rather than 25/33 if UIKit delivers touches at 60 Hz (C02, G11 must measure it). The '120 Hz = exactly one 8.3 ms JND' argument is wrong arithmetic and should be deleted; the true saving is 2-3 JNDs (C23).

2. **The destination-fill budget is built on an 80 KB tile that the stated codec tier does not produce, and the TTS gate row is unreachable as written.** Dense H&E 512² tiles at q85-90 4:4:4 are 95-117 KB p50 (CAMELYON16 tumor_014, 150 real viewports: 1.85-2.29 MB per 20-tile fill, not 1.6 MB), so the W-4G p50 transfer is 590-730 ms, not 510 (C14, C04); the moving tier is 0.55-0.68× of settled (not 0.88×) and the DPR-2 cap, not q75, is what makes the mitigated fill ≈0.6-0.7 MB (C14). The gate row '≤250 / ≤700' under a p50/p95 header cannot be met by any cold fill at the p95 network (centre 9 tiles alone 1.0-1.3 s) and must be restated as a population statistic with the cold-miss share bounded (C04). W-BB/W-iPad p95 cells omit first byte, decode and upload (650 → ≈800 ms) and 'a cold level lands inside the 155/196 ms lead at p50' is true only for the centre bundle (C05, C15). §4.3 and §4.4 carry two different RTT sets (45/200 vs 35/120; 25/50 vs 12/30) and a 19 ms first byte sits below a 25 ms RTT (C15, C22).

3. **Several Stage-0 gates measure the wrong thing or the wrong process.** G6 'WebContent RSS ≤300 MB' cannot see the GPU textures (iOS runs WebGL in the GPU Process by default) and W-iPad L0 256 + L1 64 MiB = 320 MiB already exceeds it; the phone working set needs two 64-layer arrays = 128 MiB allocated at either DPR (zero headroom) and process RSS is 1.3-1.8× nominal texture bytes (C09). G2's '5-8 ms compile' was V8 lazy validation; eager Liftoff of the 3 MB module is 87-118 ms single-thread on x86, so the phone estimate is 180-1,200 ms, not 50-100 ms (C13). G5's '≤2 ms per 512² upload' is already marginal on an A13 iPad per a public WebKit bug (2.3 ms/tile) and must name the upload source type (C10). G9's '≥1.8× on 3 workers' was measured idle (2.2×) and collapses to 1.2-1.6× under core contention (C11, C18). G7/G8 are strengthened: libjpeg-turbo identity now holds on 695 JPEGs across x86 SIMD/scalar, aarch64 NEON/scalar (qemu), jSquash and wasm-vips, Blink's decoder settings are verified, but the WebCodecs ImageDecoder path must be excluded and lossy HTJ2K is not hash-identical across ISAs (C12).

4. **Three load-bearing status facts were wrong or stale.** wgpu's `create_texture_from_webgl_handle` interop is unreleased trunk code, not in v30 — the B→C escape hatch is not additive today (C19). Safari ITP deletes script storage after 30 operating days for an ordinary origin (7 only for link-decoration-flagged origins) and exempts installed Home-Screen web apps, which makes iPad classroom offline packs viable in a PWA (C17). The MSK '+130 ms/FOV from transcoding' is not the paper's attribution; its own same-vendor comparison gives +59-100 ms (C22). Also material: the gap-2 bundle sizes were pre-wasm-bindgen (deployable dual build 0.80 MB gz, WebGPU-only 34 KB gz, a web-sys WebGL2 floor renderer 13.7 KB gz — G1 is governed by the core/format crates, and the 0.6 MB target is reachable) (C13); R2 calls do count toward the Worker 6-connection cap but queue rather than stall, and raw range reads of >512 MB DICOM levels are uncacheable below Enterprise (C21); WRY child-webview layering has no Wayland path (C20); the two OpenSeadragon overhead figures are two phases (end-state 0.3-0.5 ms, animating p99 4-32 ms) and any "X× faster than OSD" claim must use the tuned profile (C24).

Counts of individual lens verdicts (72 total): supported 22, adjusted 44, inconclusive 6, refuted 0.

### C01 — Browser present floor ≈2 vsyncs; web warm I2P 40/50 and 45/55 ms (model) — **adjusted**

- **Arithmetic — adjusted (0.6).** The row sums close (4-16 + 1-3 + 33.3 = 38-52 ms) but only as a floor: the model omits the digitizer sample wait (0-8 ms; WALT measured 22 ms contact→ACTION_DOWN on a Nexus 9), scan-out position (U(0,16.7)), panel response (2-8 ms) and the SurfaceFlinger/CoreAnimation latch that the corpus's own native tables count. A 200k-sample stage model gives p50/p95 48/61 ms without and 65/78 ms with the OS latch; 1/2/3-vsync grid 21-33 / 37-49 / 54-66 ms. Method: `lens-first-principles/recompute_C01_C08.py`.
- **Sources — adjusted (0.55).** Chromium `life_of_a_frame.md` / `how_cc_works.md` confirm the 2-vsync structure only as the designed low-latency path; `RendererCompositorQueueingDelay` is 0-1 vsync and 'high latency mode … increasing pipelining' adds one at p95 → p95 should be carried as ≈65-70 ms at 60 Hz. No primary browser touch-to-photon measurement exists; every secondary figure is ≥55 ms (WALT 61.6 ms native, Agawi iPhone 5 55 ms, Dan Luu iPad finger 70 ms). Chromium notes presentation feedback is 'incomplete/inaccurate' on Mac/iOS/Android WebView.
- **Empirical — adjusted (0.6).** Playwright/CDP EventLatency traces on Chromium 153 (REF CSS-transform page vs WebGL-in-handler vs WebGL-in-rAF): wheel input is rAF-aligned (`RendererCompositorToMain` 16.0 ms p50), generation→main-end 25-27 ms p50 for wheel vs 4.5 ms p50 for pointer with a pending rAF (inside 4-16) and 1.1 ms with none; REF vs GL-in-rAF differed by 3 ms p50 (the 'we add nothing of our own' contract held). The present floor itself is unmeasurable headless (SwiftShader swap, no vsync). Artifacts: `artifacts/C01/eventlatency_results.json`, `trace_*.json`.
- **Resolution.** All three agree the number is a floor. Relative gate (REF + 1 frame) survives; absolute rows and the '≈45 → ≈25 ms' narrative change.
- **Plan changes.** §4.4 rows 1-3 (copied in 02, 04, 05, 06): label 40/50, 45/55 'floor configuration'; add typical ≈48/61 desktop, ≈55-65/70-78 phone/iPad; add wheel row (input→tick ≈27 ms, warm ≈60 ms p50); narrative 'web ≈55-65 → native ≈25-33 ms'. Keep '[unverified; Stage 0 G11]'.

### C02 — Native shells: iPad floor 2 / typical 3 intervals, Android 3/4; N-iPad 25/33 — **contested**

- **Arithmetic — supported (0.6).** gap-4's own decomposition spans 1-3 intervals; sampled model gives iPad min/p50/p95 10.5/20.1/26.0 ms and Android 120 Hz 18.8/28.5/34.3 (60 Hz 35.6/53.5/65.0), so the plan's floor/typical are one interval conservative (≈p25). Relative to the corrected web row the native gain is 25-35 ms.
- **Sources — adjusted (0.6).** Apple docs confirm every API fact: `CAMetalDisplayLink.preferredFrameLatency` 'only acceptable values are 1.0 and 2.0', `maximumDrawableCount` '2 or 3 only… default 3', `displaySyncEnabled` macOS/Catalyst only; Android frame-pacing doc confirms the extra queued frame. But 'UIKit usually delivers touches to your app at around 60 Hz' makes the input term 0-16.7 ms (mean 8), not 0-8.3 → N-iPad typical ≈33/42 ms; web→native iPad gain ≈12 ms unless the shell also halves input. Secondary camera measurements of Apple's own apps (Pencil 30-49 ms) sit at 3.6-5.9 intervals.
- **Empirical — inconclusive (0.2).** No Apple/Android hardware, no photodiode; nothing on an x86 SwiftShader box bears on it.
- **Resolution.** The disagreement is confined to the input term. Keep the native rows as API-floor values, add the 60 Hz-delivery 'typical' alternative, and make G11's reference-quad app measure touch-delivery rate on ProMotion. The iPad-shell justification survives because C01 raised the web rows more than this lowers the native gain.
- **Plan changes.** §4.4 native table + 'Reading' (02, 04, 05, 06, 07): N-iPad '25/33 (API floor) / ≈33/42 typical if UIKit delivers at 60 Hz'; add strict floors ≈11 ms iPad, ≈19 ms Android; G11 wording (08).

### C06 — Prefetch-lead arithmetic (155 ms pinch, 196 ms gap, Brunyé/Kayser statistics) — **contested**
