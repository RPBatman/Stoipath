## Secret scan: findings and what to do about them

Patterns: AWS access key ids and secret-key assignments, GitHub tokens (`ghp_`/`gho_`/`ghu_`/`ghs_`/`ghr_`, `github_pat_`),
private-key PEM blocks, bearer tokens, Anthropic / OpenAI-style keys, Slack tokens, Google API keys, JWTs, Stripe live keys and
generic `api_key=`/`secret=`/`token=`/`password=` assignments with a long value; plus file names (`.env*`, `*.pem`, `*.key`,
`id_rsa*`, `*.p12`, `.npmrc`, `.netrc`, credentials files). Scope: all tracked files (`git ls-files`) plus the untracked,
not-ignored files about to be committed. Only file, line, pattern name and match length are reported; no value is printed or
stored anywhere.

- **2 findings: `docs/verification/artifacts/C04/key.pem` and `docs/verification/artifacts/C15/key.pem`** (private-key block).
  Each is the key of a self-signed certificate (`CN = localhost`, issuer = subject) that the C04 cold-fill and C15 network
  benchmarks use to run a local HTTP/2 server (`coldfill_bench.mjs`, `h2server.mjs`). The certificates expired on 2026-10-28
  and 2026-10-27; they grant access to nothing. They are still private keys in a public repository and any scanner (gitleaks
  included) will report them, so E7's "secret findings = 0" is **not met as is**. Recommended fix (owner/orchestrator decision,
  not applied here): delete both `key.pem`/`cert.pem` pairs and generate a throwaway pair at benchmark start
  (`openssl req -x509 -newkey rsa:2048 -nodes -subj /CN=localhost -days 1 …`), or add a `.gitleaks.toml` allowlist entry for
  these two paths with the reason. The files remain in git history either way; that is harmless for expired localhost keys.
- No AWS, GitHub, Anthropic, Slack, Google or bearer credentials; no `.env` file is tracked.
- Not covered: git history before the current tree (only current files are scanned), and binary files (tiles, images).
