# 01 — Slide formats and reader libraries

Research dimension for the Stoipath WSI viewer plan. Date: 2026-10-24. Audience: engineers / technical PO.
Verification: release dates and versions below were pulled from PyPI / crates.io metadata and GitHub source on 2026-10-24; OpenSlide format internals are from the OpenSlide project docs (fetched from the `openslide.github.io` source repo because openslide.org is blocked from this sandbox). Anything marked **[unverified]** is from memory, secondary sources, or inference and must be checked before it drives a decision.

---

## Summary

1. **The codec, not the container, sets the latency floor.** Only baseline JPEG is decodable natively (hardware/OS decoder, `<img>`/`createImageBitmap`) on every target including iPad Safari and low-end Android. JPEG 2000 has had *zero* browser-native support since Safari 18 dropped it (2024). JPEG XL is in Safari 17+ and announced for Chrome 155 (Oct 2026) but not Firefox stable. JPEG XR has no browser support and an unmaintained reference library. Everything that is not JPEG needs a WASM/GPU decoder on the client or a transcode on the server.
2. **"Zero re-encoding passthrough" is realistic for roughly the TIFF-JPEG family plus DICOM:** Aperio SVS (JPEG variant), Philips TIFF, Leica SCN, Huron/Motic/Mikroscan/ARGOS TIFF, OME-TIFF/generic tiled TIFF, and DICOM WSI. These need only a microsecond-scale header splice (TIFF `JPEGTables` + tile entropy data) or nothing at all (DICOM frames carry full JPEG headers). Hamamatsu NDPI is a special third tier: its levels are single giant JPEGs cut by restart markers into 8-pixel-high strips, so tiles can be produced *losslessly* but only via a DCT-domain re-mux (libjpeg-turbo lossless transforms), which is what Sectra's `opentile` does.
3. **Four clinically important formats can never be passed through** and must be decoded and re-encoded at ingest: Philips iSyntax (wavelet codeblocks, no JPEG anywhere), 3DHISTECH MRXS (overlapping camera frames at arbitrary positions, JPEG/PNG/BMP, sometimes JPEG XR), Zeiss CZI (overlapping sub-blocks at arbitrary positions, mostly JPEG XR), and Roche/Ventana BIF (overlapping tiles needing stitch metadata). Sakura `.svslide` (one grayscale JPEG per colour channel per tile), Trestle (overlaps), VMS/VMU and J2K-compressed SVS/VSI/DICOM also fall here from the browser's point of view.
4. **Pyramid geometry is the second blocker for instant zoom.** Aperio SVS and Leica SCN commonly step by 4x between levels, CZI may have no pyramid at all, Philips TIFF levels have padded, non-proportional dimensions, MRXS levels embed non-integral overlaps. A viewer that insists on no blur needs a level within [1x, 2x] of every target scale, so most native files need synthesized intermediate levels regardless of codec.
5. **OpenSlide (LGPL-2.1) remains the broadest single reader** (4.0.1, June 2026: adds ARGOS, Huron, CZI uncompressed/zstd, DICOM multi-file levels, NDPI > 4 GB; Python 1.4.7 released today, 2026-10-24) but it decodes to premultiplied ARGB only; it has no raw-tile API, no iSyntax, no VSI, no OME-Zarr, no JPEG XR. It is the right *decode-fallback* for ingest, not the basis of a passthrough tile server or a mobile SDK.
6. **Permissive, raw-tile-capable readers exist for the passthrough tier:** `tifffile` (BSD-3, exposes `dataoffsets`/`databytecounts`/`jpegtables`), `tiffslide` (BSD-3), `opentile` (Apache-2.0; lossless tiles from SVS/NDPI/Philips/SCN/Huron/Motic/Argos), `wsidicom` (Apache-2.0; `read_encoded_tile`, DICOMweb). For iSyntax, `libisyntax` (BSD-2, C) is the only permissive option; the Philips SDK is proprietary and reportedly LGPL-incompatible [secondary source]. Bio-Formats remains the catch-all but every proprietary WSI reader in it (SVS, NDPI, MRXS, VSI, CZI, SCN, BIF, Trestle) lives in the **GPL-2** `formats-gpl` component; only DICOM/OME-TIFF/TIFF are BSD.
7. **Licensing drives architecture:** keep LGPL (OpenSlide, libvips, libCZI-LGPL-3) and GPL (Bio-Formats) code server-side in isolated worker processes; ship the client SDKs (web/iOS/Android/native) with only permissive decoders (libjpeg-turbo, OpenJPH, OpenJPEG, libjxl, zstd) reading a canonical converted format. LGPL in an iOS static binary or a WASM bundle is a legal grey zone; LGPL-3 is widely considered App-Store-incompatible.
8. **Recommendation in one line:** ingest everything into a canonical, standards-based pyramid (DICOM WSI or OME-TIFF/OME-Zarr; container choice belongs to the storage dimension) with a full 2x pyramid, uniform tiles and JPEG for 8-bit RGB (HTJ2K/JXL/zstd for 16-bit multichannel), using *lossless* passthrough for the TIFF-JPEG/DICOM/NDPI tier and decode-once for the rest; serve native files on the fly only for the passthrough tier (with synthesized missing levels), and treat on-the-fly OpenSlide decode as a degraded temporary mode.

## Findings

### F1. Format internals, codecs and passthrough status

Legend for the *Passthrough* column: **A** = tile bytes are complete images, serve as-is; **B** = lossless header splice (prepend TIFF `JPEGTables`/SOI, fix colour markers; microseconds, no pixel decode); **C** = lossless re-mux in DCT domain (entropy decode + re-encode of coefficients, no IDCT/quantisation; low ms); **D** = decode + re-encode required (generation loss unless lossless codec). *Browser-native* = can a browser decode the tile bytes without WASM.

### F5. Licensing implications for an embeddable cross-platform SDK

- **LGPL-2.1 (OpenSlide, libvips, openslide-js):** fine for servers and desktop apps with dynamic linking. In iOS static binaries and WASM bundles the user must be able to relink against a modified library; the FFmpeg/Qt communities treat App Store distribution of statically linked LGPL code as unresolved (never litigated). Dynamic frameworks (iOS ≥ 8) reduce but do not remove the concern. Decision: keep LGPL out of the shipped client SDKs.
- **LGPL-3 (libCZI):** adds anti-tivoisation terms; widely regarded as incompatible with App Store distribution. Server-only, or buy Zeiss's commercial licence.
- **GPL-2 (Bio-Formats `formats-gpl`, hence bioformats2raw/raw2ometiff):** must be isolated behind a process/network boundary (CLI or microservice) or licensed commercially from Glencoe. Acceptable for ingest, never in a linked SDK.
- **Proprietary (Philips Pathology SDK):** registration-gated download, reportedly forbids combination with LGPL code and redistribution (2021 OpenSlide list post, secondhand). Use only inside a sealed ingest worker if at all; prefer libisyntax (BSD-2) after validation.
- **Permissive core (BSD/MIT/Apache):** tifffile/imagecodecs, tiffslide, opentile, wsidicom(izer), large-image, cuCIM, slideio, libisyntax, libdicom, OpenJPEG, OpenJPH, libjpeg-turbo, libjxl, zstd, zarr/zarrs, dicom-rs, wsi-rs, dicom-microscopy-viewer. This set covers every passthrough-tier format plus iSyntax, CZI (slideio/czifile) and VSI (slideio) without copyleft.

## Implications for our viewer

**Instant zoom (goal 1).** The viewer can only be lag-free if (i) every tile it needs is a complete, browser-/OS-native JPEG (or a codec with a fast WASM/GPU decoder we control), (ii) a pyramid level exists within [1x, 2x] of every on-screen scale so no tile is ever rendered more than 2x magnified, and (iii) tile addressing is O(1) with a small, cacheable index. Native formats violate at least one of these in almost every case: SVS/SCN step by 4x, CZI may have no pyramid, Philips TIFF has padded level geometry, NDPI "tiles" are 8-pixel strips, MRXS/BIF/CZI tiles overlap, J2K/JXR/iSyntax need heavy decoders, OME-Zarr raw chunks cost 5–10x the bytes. Therefore **instant zoom is a property of the ingested representation, not of the reader**: the reader strategy's job is to get every input into a canonical pyramid with the least loss and the least compute, and to do it fast enough that first view is not blocked.

**Cross-platform (goal 2).** The client SDKs (web, iOS, Android, desktop, Jupyter widget) must read one canonical format with a tiny permissive decoder set (libjpeg-turbo or OS JPEG, OpenJPH for HTJ2K, zstd, optionally libjxl). All vendor-format knowledge, copyleft code (OpenSlide, libvips, libCZI, Bio-Formats) and proprietary SDKs stay in server-side ingest workers. Client-side native-format reading (openslide-js WASM, wsi-rs) is a desktop/offline nicety, never the mobile hot path: openslide-js requires cross-origin isolation and SharedArrayBuffer and carries LGPL into the bundle.

**Versatility (goal 3).** DICOM WSI is the only standard that already encodes brightfield, multichannel fluorescence (optical paths), z-planes, annotations (Bulk Simple Annotations, SR), segmentations and parametric maps, and whose network API (WADO-RS frames) is passthrough by construction; the IDC Slim viewer proves end-to-end browser decode of JPEG/J2K/HTJ2K/JXL frames. OME-Zarr (v0.5, Zarr v3, sharding) is the better fit for 16-bit multichannel analysis and cloud-native access but has no browser-native codec. The ingest pipeline should be able to emit both; which is primary is a storage-dimension decision.

**Generation loss.** Byte passthrough (tiers A–C) preserves the scanner's pixels exactly, which matters for regulatory validation and for AI reproducibility. Only iSyntax, MRXS, CZI, BIF, svslide, Trestle, VMS/VMU and J2K/JXR sources require a lossy or lossless re-encode; for J2K sources, HTJ2K's designed lossless transcode path from Part 1 should be tested so that TCGA-style archives keep their original quantisation while gaining ≈10x decode speed.

## Recommendations

### (a) Ingest / convert pipeline

1. **Three-tier reader chain, chosen per file by sniffing, always preferring the most lossless tier:**
   - *Tier A/B — byte passthrough:* DICOM WSI (any codec), SVS-JPEG, Philips TIFF, SCN, Huron/Motic/Mikroscan/ARGOS, OME-TIFF and generic tiled TIFF with JPEG/WebP/JXL tiles. Implement our own TIFF/BigTIFF/NDPI-offset and DICOM Part-10/TILED_FULL parsers in the server language (Rust recommended: `tiff`, `dicom-rs`, `turbojpeg`, `zarrs` are all permissive and current); use `tifffile`, `opentile` and `wsidicom` as behavioural oracles in CI (byte-identical tile output).
   - *Tier C — lossless re-mux:* NDPI JPEG levels via libjpeg-turbo lossless crop/concat of restart-marker strips into square tiles (opentile's algorithm). Fall back to Tier D for JPEG XR levels and low levels without restart markers.
   - *Tier D — decode once:* OpenSlide 4.0.1 (MRXS, BIF, svslide, Trestle, VMS/VMU, CZI zstd/uncompressed) in an isolated LGPL worker; libisyntax (BSD-2) for iSyntax, with a Philips-SDK-based worker (isyntax2raw / wsidicomizer[isyntax]) available only as a validation oracle and emergency fallback under its own licence review; slideio or libCZI (LGPL-3, isolated) for CZI with JXR, slideio/Bio-Formats for VSI and fluorescence SCN; Bio-Formats (GPL, separate JVM container, bioformats2raw) as the last-resort catch-all. cuCIM/nvJPEG2000 for GPU batch decode of J2K-heavy archives when throughput matters.
2. **Output contract (inputs to the storage/tiling dimension):** full 2x pyramid down to a ≤ 1k-pixel top level (synthesise missing levels from the nearest finer native level, never from coarser), uniform tile grid (256 or 512; decision belongs to the rendering dimension), 8-bit RGB as JPEG q ≥ 90 with 4:4:4 or 4:2:2 chroma **[quality policy to be validated with pathologists]**, 16-bit/multichannel as HTJ2K lossless or zstd chunks, ICC profile preserved, label/macro/thumbnail preserved, source-format metadata preserved as key-value properties (OpenSlide naming), per-tile provenance flag (passthrough vs re-encoded).
3. **Lossless-first policy and verification:** record the tier used; for Tier D re-encodes keep a checksum of decoded pixels for audit; for J2K sources evaluate J2K Part 1 → HTJ2K lossless transcoding (OpenJPH/Kakadu) before defaulting to JPEG re-encode.
4. **Process isolation and licence hygiene:** one container image per licence class (permissive core; LGPL workers; GPL Bio-Formats; proprietary Philips SDK), communicating over a tile/level RPC. Ship nothing but the permissive core in client SDKs.
5. **Priority order by expected volume:** DICOM + SVS + NDPI + Philips (TIFF then iSyntax) first; MRXS and BIF second; CZI/VSI/OME-Zarr for the fluorescence roadmap; svslide/Trestle/VMS last.

### (b) On-the-fly serving from native files

1. **Serve natively only Tier A–C formats**, with a per-slide index cache (parsed IFDs / DICOM offset tables, restart-marker maps for NDPI) and an on-demand level synthesiser that generates and caches the missing 2x levels from native tiles on first access; treat this as "lazy ingest": the same code path writes the canonical pyramid in the background so the slide upgrades itself.
2. **For Tier D formats, do not promise instant zoom.** If a product requirement forces immediate viewing, run OpenSlide decode + JPEG re-encode in a sidecar as an explicitly degraded mode (expect several ms server CPU per tile plus one generation loss) and kick off full conversion immediately. Never attempt Tier D in the client.
3. **DICOMweb sources:** proxy or let the client talk WADO-RS `/frames/{n}` directly (Slim/dicom-microscopy-viewer precedent); negotiate `Accept` for stored transfer syntax to avoid server transcoding, and decode HTJ2K/J2K/JXL frames with WASM only when the archive refuses to transcode to JPEG.
4. **Remote native files (S3/HTTP range):** tifffile/tiffslide already demonstrate fsspec range reads; the index-read cost for a 100k² slide (≈ MBs of tile offsets per level) must be amortised with a persistent index cache; TILED_FULL DICOM and sharded OME-Zarr are the only inputs with a cheap enough index to consider client-direct range reads.

## Open questions

1. **Real format mix of target customers.** No verified installed-base data; need a sample of actual slide inventories (clinical vs research) before fixing the ingest priority order and the iSyntax investment.
2. **iSyntax strategy.** Is libisyntax complete and bit-accurate for all iSyntax versions (incl. newer i2Syntax **[unverified]**) and fast enough? Current Philips SDK licence text and whether a sealed worker is acceptable; whether Philips's move to DICOM (2026 conformance statements listing JPEG XL) makes iSyntax ingest a shrinking problem.
3. **NDPI JPEG XR prevalence** on current NanoZoomer firmware (opentile documents it; OpenSlide does not), and the share of NDPI low levels without restart markers.
4. **Aperio GT450 specifics:** tile size (256?) and level factors; whether label/macro handling on "newer slides" (OpenSlide 4.0.1 note) affects us.
5. **HTJ2K lossless transcoding from J2K Part 1** with open tooling (OpenJPH/OpenJPEG) at scale, and client-side openjphjs performance on low-end Android.
6. **wsi-rs maturity**: single-vendor, ≈2k downloads; could become the permissive native engine for desktop/Jupyter SDKs. Needs a corpus-based evaluation against OpenSlide and tifffile.
7. **Legal position on LGPL in WASM bundles and iOS static frameworks** (openslide-js, libvips-wasm) — obtain counsel before any client-side use.
8. **JPEG XL as delivery codec:** Chrome 155 stable date and Firefox timeline; whether DICOM .111 (lossless JPEG recompression) is worth adopting for archive storage.
9. **Bio-Formats 8 precompressed-tile APIs:** whether bioformats2raw/raw2ometiff can carry NDPI/DICOM tiles through losslessly, which would let a single GPL-isolated pipeline cover more of Tier A–C.
10. **Fluorescence/multichannel scope** (CZI, QPTIFF, OME-TIFF, SCN-F, DICOM optical paths) and its share of early users, which decides how much of the OME-Zarr/HTJ2K 16-bit path is needed in v1.
11. **Canonical container decision** (DICOM WSI vs OME-TIFF vs OME-Zarr vs both) — owned by the storage/tiling dimension; this note only constrains it (full 2x pyramid, uniform grid, JPEG for 8-bit RGB, passthrough-friendly).
