### C01 — Browser present floor ≈2 vsyncs → warm I2P 40/50 (W-LAN, W-BB), 45/55 ms (W-4G, W-iPad)

- **Kind:** model
- **Claim:** The browser present path for already-resident tiles costs ≈2 vsyncs (33 ms at 60 Hz), so the warm input-to-photon (I2P) on the web rows is 40/50 ms p50/p95 on W-LAN and W-BB and 45/55 ms on W-4G and W-iPad, composed as input→tick 4–16 ms + tick ≤1–3 ms (wasm) + 33 ms present; the gate is 'warm I2P ≤ REF + 1 frame at p95' where REF is a trivial CSS-transform page measured on the same device. The 2-vsync floor is tagged [unverified; Stage 0] and the perf judge found proposal A's 17–33 ms present row (warm 25–45 ms) one frame optimistic.
- **Source:** arch/recommended.md §4.4 rows 1–3 and §10 risk 1; arch/A-web-core.md §3 latency table (17–33 ms row); research/04-instant-zoom-client.md F1 ('roughly two vsyncs … [unverified, widely reported]'); judge/judgments.json perf→A rationale
- **Load-bearing because:** It is the only latency term the native shells remove (the stated reason the iPad shell exists at month 12 and the '≈45 → ≈25 ms' claim). If the Chromium/WebKit floor is 1 vsync the native-shell latency case shrinks to ≈8 ms (one JND) and rests on memory/pen only; if it is 3 vsyncs every web warm row is ≥16.7 ms off and the 'we add nothing of our own' contract cannot be shown with the REF+1 gate as written.
- **Test plan:** Arithmetic: input 4–16 + tick 1–3 + 2×16.7 = 38–52 ms (table 40/50 consistent); with 1 vsync 22–36 ms, with 3 vsyncs 55–69 ms — tabulate all three so the Stage-0 measurement can be classified. Primary source: Chromium rendering-pipeline docs (BeginFrame/compositor/display scheduler, 'input latency' design notes) and any published Chrome-Android or iOS-Safari touch-to-photon measurement (the perf judge found none); WALT usage doc gives a 2016 Nexus 9 'screen response' median of 61.6 ms at 60 Hz as an outer bound. On this machine: no device and no photons; a headless Chromium (if a Playwright binary can be fetched through the proxy) with SwiftShader can only report rAF→Event-Timing stage durations, not photon latency, and x86 software GL is not a phone GPU — this claim is bounded here, not refuted. The real test is gate G11 (photodiode/240 fps rig) on the W-4G and W-iPad devices.

### C02 — Native floors: iPad 2/3 intervals (16.7/25 ms), Android 3/4 (25/33 ms) → N-iPad 25/33, N-And 40/55 ms

- **Kind:** model
- **Claim:** Native shells: iPad native Metal floor is 2 display intervals (16.7 ms at 120 Hz) with 3 typical (25 ms), Android SurfaceView+Vulkan floor 3 intervals / 4 typical (25/33 ms); hence warm I2P gates N-Desk 20/30 ms, N-iPad 25/33 ms, N-And 40/55 ms (65/90 ms when the OEM holds 60 Hz), with the gate '≤ REF-quad p95 + 1 interval' (REF-quad = raw Metal/Vulkan textured quad on the same device). Basis: CAMetalDisplayLink.preferredFrameLatency accepts only 1.0/2.0, maximumDrawableCount 2–3, displaySyncEnabled is macOS-only (no tearing mode on iOS), SurfaceFlinger adds one latch.
- **Source:** arch/recommended.md §4.4 native table and 'Reading' paragraph; research/11-gap-4-native-mobile-render-pipeline.md §2.1, §2.9 ([model from verified API semantics]; 'no public photodiode/camera measurement reachable'), §4 rec. 1
- **Load-bearing because:** The improvement from ≈45 ms (web iPad) to ≈25 ms (native) is the headline justification for pulling the iPad shell to month 12 (+11 PM) and for the N tier; if typical native I2P is 4 intervals (33 ms) the gain is one frame and inside the noise of the web floor's own uncertainty (C01); if UIKit delivers touches at 120 Hz the input term halves and the gain grows.
- **Test plan:** Arithmetic: 0–1 interval input + 1 interval encode/GPU + 0–1 present/scan-out = 2–3 intervals; Android +1 for SurfaceFlinger; note WALT's Nexus 9 figure (physical tap → ACTION_DOWN 22 ms at 60 Hz) already exceeds the '0–1 interval' input term, so re-derive with a 1–2 interval input term. Primary source: Apple docs for CAMetalDisplayLink.preferredFrameLatency, CAMetalLayer.maximumDrawableCount/displaySyncEnabled, UIEvent.coalescedTouches ('around 60 Hz' delivery); Android Swappy frame-pacing doc ('extra frame of latency'); Dan Luu's latency table and Apple's 9 ms Pencil figure as secondary bounds. ### C04 — W-4G cold fill ≈650/3,000 ms (mitigated 450/2,000) vs TTS gate ≤250/≤700 — bandwidth arithmetic

- **Kind:** arithmetic

The stated radio promise is 'centre sharp ≈300 ms after burst end, full viewport ≤700 ms p50'.
- **Source:** arch/recommended.md §4.4 W-4G column and 'Reading' paragraph; §4.3 inputs (45/200 ms RTT, 25/5 Mbps); research/02-pyramid-storage-serving.md F9; research/05-instant-zoom-systems.md F2 Table 1
- **Load-bearing because:** This row defines the whole radio-link promise and the moving-tier/DPR-cap mitigations; it is also the row most exposed to tile-byte error (C14) and bandwidth-percentile error (C15). Note the internal tension: the gate row reads '≤250 / ≤700' under a 'p50 / p95' header while the prose says '≤700 ms p50'; by the table's own numbers even the 9-tile centre at p95 is 226 + 800 + ~150 ≈ 1,180 ms, so a p95 ≤700 gate cannot be met on W-4G by this arithmetic unless the burst itself (0.5–2 s) absorbs the transfer (TTS is measured from the last input, cold fill from the first).
- **Test plan:** Arithmetic: 1.6e6×8/25e6 = 512 ms and /5e6 = 2,560 ms; 0.5 MB → 160/800 ms; p50 sum 57 + 510 + ~100 (decode partly overlapped) ≈ 650; p95 226 + 2,600 + 150 ≈ 3,000; mitigated 57 + 320 + ~80 ≈ 450 — all reproduce. Then re-run with 2.2 MB (q90 4:4:4 tiles, C14): p50 transfer 704 ms → cold fill ≈850 ms, past the ≤700 figure at p50. Separately model TTS (from last input) for burst durations of 0.5/1/2 s to see which gate interpretation is achievable. Primary source: Ookla/Opensignal 2025–26 4G/5G download percentiles (p50 and p10/p5) to test the 25/5 Mbps pair. ### C06 — Prefetch lead 155 ms (pinch) / 196 ms (wheel gap); 66.4 % of bursts ≥2.3 levels; 74 % naive waste

- **Kind:** model
- **Claim:** Prefetch lead arithmetic: a two-finger pinch doubles scale in ≈300 ms (≈3.3 levels/s); from a typical s ≈ 0.7 the target crosses s = 1.0 after a 1.43× zoom, ≈155 ms into the gesture; for wheel bursts the minimum inter-burst gap is 196 ms and 90 % of bursts are followed by another within 5 s (Brunyé 2023, 89 pathologists, 21,416 zoom events); 66.4 % of bursts span ≥5× (≥2.3 pyramid levels) and 33.6 % span 1–4×, so the destination predictor needs ≥2 consistent samples and Stage-1 prefetch waste must be ≤50 % (the only field measurement, Kayser/Wienert 2009, is 74 % waste for naive prefetch). Pathologist pinch rate is unmeasured [unverified].
- **Source:** research/04-instant-zoom-client.md F3 timing model [model]; research/11-gap-1-pathologist-human-factors.md F1, F7 ('pinch rate … no pathology data'), F8 item 5; arch/recommended.md §4.1 Prefetch, §4.2 item 4, §4.4 'Reading'
- **Load-bearing because:** The entire 'cold level lands inside the gap' argument for W-LAN/N-Desk (cold fill 85/40 ms < 155 ms) and the p50 claim for W-BB depend on the lead. If pathologists pinch at 6 levels/s the lead is ≈86 ms and even the LAN cold fill (85 ms p50) only just fits; if s at gesture start is 0.5 (right after a level switch) the lead is 300 ms. The 34 % short-burst base rate drives §4.2 correction 4 (predictor gating).
- **Test plan:** Arithmetic: log2(1/0.7) = 0.515 levels ÷ 3.33 levels/s = 154 ms (reproduces 155); sensitivity grid over s ∈ {0.5, 0.7, 0.9} × rate ∈ {2, 3.3, 6} levels/s gives 50–500 ms; check that 1.2×/notch × 2 notches = 0.53 levels matches 'ample time'. Primary source: Brunyé et al. 2023 PLoS One (PMC9997932, open access — verify 196 ms minimum gap, 100 ms minimum duration, 66.4 %/33.6 % amplitude split, 21,416 events, 90.4 % within 5 s); Kayser/Wienert 2009 Diagn Pathol (PMC2654030: 25.9 % of prefetched area viewed, 22 % of path area prefetchable); Raghunath 2012 (293 px gaze–cursor median).
