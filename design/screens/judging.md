# Concept judging — 2026-11-01

Three judges (practising pathologist/educator, UX and accessibility specialist, front-end/engine engineer) scored each concept 1–10 on six criteria. Weighted score = 0.30 workflow fit + 0.20 clarity + 0.15 accessibility + 0.15 feasibility + 0.15 device fit + 0.05 distinctiveness. The final screen in `final/` starts from the winner and grafts the judges' ideas from the others.

**engineering verdict.** Recommend Concept C (Task-flow) as the base for the final clinical sign-out screen, with grafts from A and B. From the front-end/engine lens C is the design that covers the entire must-show list on one standard rail/dock frame with the least custom component work that still has a credible tablet/pen story: a single dock, static step panels, per-step tool visibility by attribute, templated dialogs, .is-gesturing implemented on drag/wheel/flyTo, and no chrome geometry change during gestures at any of the five viewports (headless probe). Its one performance defect (paintView writing dock button state every frame, 216 attribute writes per short gesture) is a one-afternoon fix: only HUD text may update per frame, everything else at settle. Concept A is the cheapest shell (40 custom classes, 92.6 % canvas at 1920) and its single command registry, command echo and summon-tab key hints should be carried over, but it depends on an engine-drawn radial for tool access, grows a HUD box during gestures, rebuilds drawers per wheel notch, binds keys inside the iframe, and leaves AI-assisted screening and the unviewed-slide hazard weak. Concept B is the best-structured mock (HUD-only updates during drag, no keys in the iframe) and contributes the Dx-gate checklist, the live non-modal hand-off section and the AI-flagged-regions-viewed line, but as an MVP shell it is the most expensive by a wide margin (two docks, movable sections, resizers that resize the engine surface per frame, a runtime governor, five persisted presets, analytics) and two of its panels assume a clinical-context/timestamp read API that the launch-context contract does not provide; its 70 to 75 % canvas on 1440/1920 displays is also the weakest of the three. Design notes for the final: replace C's per-frame dock writes with settle-time updates, adopt B's no-keys-in-iframe rule for the controller iframe, treat the TAT/clinical-context data as a new integration-service contract to be filed with an FR- id, and keep A's radial as a static-time, DOM-only, post-MVP option.
