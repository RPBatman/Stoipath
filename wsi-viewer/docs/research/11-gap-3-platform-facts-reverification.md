## Summary

- **JPEG XL is default-on in Chrome 155 and Firefox 158; note 03 is right, note 02 is wrong.** Chromium ToT has `BASE_FEATURE(kJXLImageFormat, FEATURE_ENABLED_BY_DEFAULT)` with a Rust `jxl-rs` decoder; Firefox 158 release notes say "now enabled by default" and add `image/jxl` to the image `Accept` header. Safari (17 → 27.2 beta) decodes stills but not progressively. Samsung Internet 30 (Blink 143) and Edge (caniuse: no through 155) lack it. JXL is now a *negotiable* delivery codec; the lossless-JPEG-recompression archive tier moves from "2027" to "benchmark now".
- **WebCodecs `ImageDecoder` is still not in any shipping Safari** (BCD: `preview`; absent from Safari 26.x–27.2 release notes) but WebKit ToT has `WebCodecsImageEnabled: default true`, so expect it in 2027. **Firefox Android very probably exposes `ImageDecoder`**: the WebIDL exposure function checks only `dom.media.webcodecs.image-decoder.enabled` (true, no Android guard); only *video* WebCodecs is Nightly-only on Android. Notes 04/06 need correcting on that point.
- **Safari's 60 fps cap stands at WebKit ToT**: `PreferPageRenderingUpdatesNear60FPSEnabled` defaults to `true` on every platform except visionOS and feeds `Page::preferredRenderingUpdateInterval()`. WKWebView can only flip it through the private `_WKFeature` SPI. Nothing in Safari 26.x–27.2 release notes changes this. The native-shell-for-120 Hz decision is reaffirmed.
- **WebGPU compatibility mode has shipped** (`featureLevel: "compatibility"` since Chrome 146; `kWebGPUCompatibilityMode` and `kWebGPUAndroidOpenGLES` enabled by default at ToT; Android 10+ / GLES 3.1). It lowers `maxTextureDimension2D` to 4096, `maxUniformBufferBindingSize` to 16 KiB, `maxColorAttachments` to 4, and forbids several features we must design around. **Samsung Xclipse GPUs are still blocklisted** for WebGPU in every Chromium-based browser, Samsung Internet included.
- **Firefox WebGPU on Linux/Android is still Nightly-only** (pref `dom.webgpu.enabled` is `@IS_EARLY_BETA_OR_EARLIER@` outside Windows and Apple-silicon macOS). **WebKitGTK has no WebGPU at all** (`ENABLE_WEBGPU` is `PLATFORM(COCOA)`-only; GTK CMake options never enable it). The Linux Tauri shell is WebGL2 or a native `wgpu` window; the "uncertain" in note 06 becomes "no".
- **`fetch(..., {priority})` works in Safari 17.2+ and Firefox 132+, but Safari sends no RFC 9218 `Priority` header** (BCD; WebKit's `HTTPHeaderNames.in` has no such header). Server-side scheduling cannot lean on browser priority signals from Safari.
- **Safari's 7-day script-storage deletion covers OPFS and the Cache API**: WebKit's ITP `monitoredDataTypes()` lists `FileSystem`, `DOMCache`, `IndexedDBDatabases`, `LocalStorage`, `ServiceWorkerRegistrations`. `navigator.storage.persist()` only exempts an origin from quota- and time-based *storage* eviction, not from the ITP path.
- **Chrome's HTTP/3 0-RTT is on by default and applies to safe methods (GET/HEAD/OPTIONS/TRACE)**; TLS-1.3 early data over TCP (`kEnableTLS13EarlyData`) is *off*, so the HTTP/2 fallback never gets 0-RTT. Chrome races a dedicated `DNS_ALPN_H3` job off the HTTPS DNS record. Safari's 0-RTT behaviour remains unverified.
- **Chrome's HTTP cache is partitioned by (top-level site, frame site) — but only in Chrome proper**: `SplitCacheFeatureEnableByDefault()` is called from `chrome_main_delegate.cc` explicitly "so as to not impact non-Chrome embedders like WebView, Cronet". **CloudFront and Cloudflare both cache partial objects and both accept multi-range requests** under conditions; note 02's "CloudFront single-range only" is wrong, though the advice to avoid multi-range survives for different reasons.
- **Rust `atomics` for wasm32 is still `Unstable`** in rustc at Rust 1.99 (2026-10-01); threaded Wasm still needs nightly `-Zbuild-std`. npm OIDC publishing exists in the CLI since 11.5.0 (2025-07-24) with a `npm trust` command; the GA announcements for npm and crates.io could not be fetched.
- **WebGPU `timestamp-query`** is exposed by Chrome 121+ (desktop and Android) with privacy quantization forced on unless `--enable-webgpu-developer-features`, and by Safari 26+ on Apple-silicon GPUs (WebKit gates it on `MTLCounterSamplingPointAtStageBoundary`, excluding Intel Macs) with no quantization found in source. Firefox: none.

### WebGPU Compatibility Mode: what it takes away (gpuweb `proposals/compatibility-mode.md`, ToT)

| Limit | Compat | Core | Our exposure |
|---|---|---|---|
| `maxTextureDimension1D/2D` | **4096** | 8192 | Tile atlases > 4096² are out; texture arrays of 512² or 1024² tiles are fine (`maxTextureArrayLayers` is *not* lowered) |
| `maxUniformBufferBindingSize` | **16384** | 65536 | Per-tile instance data must go in storage buffers or vertex buffers, not one big UBO |
| `maxColorAttachments` | 4 | 8 | Irrelevant for a 2D viewer |
| `maxComputeInvocationsPerWorkgroup`, `maxComputeWorkgroupSizeX/Y` | 128 | 256 | Only matters if compute LUTs are used; the plan already treats compute as optional |
| `maxInterStageShaderVariables` | 15 | 16 | Irrelevant |
| `maxStorageBuffersInVertexStage` / `maxStorageTexturesInVertexStage` (new) | **0** | = per-stage limit | Instance data in the vertex stage must come from *vertex* buffers or uniforms, not storage buffers |
| `maxStorageBuffersInFragmentStage` / `maxStorageTexturesInFragmentStage` (new) | 4 | = per-stage limit | Fine |

Validation restrictions that touch a tile renderer: texture views must declare their dimension at `createTexture`; array texture views bound in bind groups must cover the whole array (`baseArrayLayer = 0`, full `arrayLayerCount`) — so per-level sub-ranges of one array texture cannot be bound separately; identical blend state across colour attachments; no `bgra8unorm-srgb`; no texture-format reinterpretation; no RG storage textures; no `sample_mask`/`sample_index`; `@interpolate(flat)` must use `flat, either`; a cap on texture+sampler combinations per stage. None of these block the fragment-shader-only, texture-array design in notes 03/04, but the "bind one slice range" and "one big UBO of tile transforms" shortcuts are off the table.

Hardware reach of compat mode on Android (Chromium `webgpu_blocklist_impl.cc`): ARM/Qualcomm/Intel on **Android 10+ via GLES** (no version check; the Vulkan path needs 12+), Imagination on **Android 13+ GLES / 16+ Vulkan**, **everything else blocked**, Xclipse included.

### CDN range-request semantics for a single-file container

| Behaviour | CloudFront (archived 2023 doc) | Cloudflare (current docs) |
|---|---|---|

## Implications for our viewer

**Instant zoom (goal 1).**

- The codec ladder changes shape but not its conclusion. JXL is now decodable by default in Chrome 155+, Firefox 158+ and Safari 17+, so `Accept`-negotiated JXL tiles become possible on the majority of desktop browsers this quarter. But JXL still decodes 6–7x slower than JPEG per 512² tile (note 02, measured) and Safari cannot decode it progressively, so JXL does nothing for *time-to-sharp* on the devices that define our floor (A12-class iPad, Mali-G5x Android, Samsung Internet). JPEG stays the hot-path delivery codec; JXL's real win is the archive tier (lossless JPEG recompression, bit-exact JPEG back), where the bytes saved cost nothing at zoom time if the tile server can emit the reconstructed JPEG.
- The decode path remains `createImageBitmap(blob)` in workers everywhere, with `ImageDecoder` as an accelerator on Chromium and now, probably, Firefox Android. Safari gets `ImageDecoder` in 2027 at the earliest; nothing in our pipeline may depend on it.
- Frame pacing: iPad Safari and WKWebView stay at ~60 fps by default at WebKit ToT, so 120 Hz on iPad still needs the native shell. On Android, Chrome has no cap and follows the display's current mode including adaptive refresh, so the 8.3 ms budget in notes 03/04 is reachable on 120 Hz phones but is *the OS's decision*, not ours; the acceptance test must record the actual rAF cadence per device.
- GPU telemetry: `timestamp-query` is coarse on Chrome (quantized unless a developer flag is set) and fine on Apple-silicon Safari. Per-tile upload timing (0.5–2 ms) cannot be measured reliably on Chrome with timestamp queries; measure per-frame batches instead, and fall back to CPU-side timing elsewhere.
- Transport: Chrome's QUIC 0-RTT applies to our tile GETs, and its `DNS_ALPN_H3` race means an `HTTPS` RR with `alpn=h3` saves the Alt-Svc round trip on first connect. Chrome's HTTP/2 fallback has no 0-RTT at all, which widens the HTTP/3-vs-HTTP/2 gap in note 02's latency model for Samsung Internet and proxied corporate networks. Safari's behaviour is unknown; model it as 1-RTT.

**Cross-platform (goal 2).**

- The WebGL2 renderer is the floor, not a fallback: Firefox Linux/Android have no WebGPU in release, WebKitGTK has none at all, Samsung Internet on Exynos is blocklisted, and compat mode on GLES 3.1 devices imposes a 4096² texture limit, a 16 KiB uniform-binding limit and whole-array bind-group views. The texture-array tile cache with instanced draws fed from vertex buffers satisfies every one of these constraints; the alternatives (one 8192² atlas, per-level array slices, a large transform UBO) do not.
- The Linux desktop shell decision moves forward: WebKitGTK cannot give us WebGPU, so either accept WebGL2 inside Tauri on Linux or render the viewport in a native `wgpu` surface from day one. Given the Rust-core architecture in note 06, the native window is the cheaper path and keeps one GPU backend per platform.
- Embedding: in Chrome, our component inside hospital A's LIS caches under key (A, our-origin); the same tiles are a miss under hospital B — as note 02 said. In Android WebView-based LIS apps the cache is *not* partitioned, which is good for hit rate and irrelevant for the design because the component already owns its cache. Safari deletes OPFS and Cache API data for an origin after 7 days without user interaction with that origin, `persist()` notwithstanding; for a third-party embed this clock runs against *our* origin, so the OPFS store must be a cache that is cheap to refill, never a store of record.
- Scheduling: Safari ignores RFC 9218 request priorities, so the server cannot rely on browser priority signals to order tile responses. The client-slot scheduler (in-flight caps per tier, cancellation via `AbortController`) is the only cross-browser mechanism; the `Priority` header from Chrome/Firefox is a bonus for the H3 server to honour.

## Recommendations (plan statements that must change)

1. **Note 02 R4 and §3 codec table.** Replace "no JPEG XL until Chrome and Firefox ship it by default (re-check Q2 2027)" with: enable `image/jxl` in `Accept` negotiation for Chrome 155+/Firefox 158+/Safari 17+ as an *opt-in bandwidth variant* behind device-class gating (same policy as AVIF); JPEG remains the default. Start the archive-tier benchmark now: lossless JPEG→JXL recompression ratio on real slides, and the cost of JXL→JPEG reconstruction on the tile server, so the archive can be JXL while delivery stays JPEG. Mark Edge and Samsung Internet as no-JXL.
2. **Note 02 request-coalescing paragraph.** Delete "CloudFront single-range only [unverified]". Both CDNs accept multi-range; still avoid it, because CloudFront falls back to a 200/full object on any malformed range and Cloudflare's multipart behaviour depends on the Origin Range Requests setting and on whether the full object is already cached. Align shard byte ranges to 1 MiB (Cloudflare's origin fetch unit) and issue single contiguous ranges.
3. **Note 02 cache-partitioning row and R6.** Keep the conclusion; add that only Chrome proper partitions (key = top-level site + frame site), that Android WebView/Cronet/other embedders do not, and that the "since Chrome 86" date is from Chrome's blog, not re-verified.
4. **Notes 03/04/06 iOS frame rate.** Keep "60 Hz unless the user flips the flag; WKWebView cannot"; add the primary evidence (`PreferPageRenderingUpdatesNear60FPSEnabled: default true`, visionOS excepted) and that the only WKWebView escape is private `_WKFeature` SPI, which an App Store app should not ship. Update every "Safari 26.x" reference to Safari 27 / 27.2 beta.
5. **Note 03 open question 2.** Close it: WebGPU in a Worker with a transferred `OffscreenCanvas` is supported in Safari 26+.
6. **Notes 03/06 Samsung Internet.** Replace "unverified" with: Chromium 143 base; WebGPU blocked on Exynos/Xclipse by Chromium's vendor blocklist regardless of Samsung's flags; plausible on Snapdragon; no JXL; no compat-mode `featureLevel` (needs 146); HTTP/3 assumed absent.
