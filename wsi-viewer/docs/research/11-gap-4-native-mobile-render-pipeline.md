## 1. Summary

1. **The "1–2 frames at 120 Hz" claim in note 06 is half right.** On iPad Pro the *documented* pipeline floor for a vsync-locked Metal app is **2 display intervals (16.7 ms at 120 Hz) from the display-link callback that consumes an input sample to photons**, plus 0–1 interval of input sampling/delivery: **best case ≈ 2 frames, typical ≈ 3 frames (25 ms)** **[model, built from verified API semantics]**. iOS offers no tear/immediate mode (`displaySyncEnabled` is macOS-only **[verified]**), so nothing below 2 intervals is reachable; `CAMetalDisplayLink.preferredFrameLatency` is restricted to exactly 1.0 or 2.0 frames **[verified]**. On Android with `SurfaceView` + Vulkan the SurfaceFlinger composition step adds one more interval: **typical ≈ 3–4 frames (25–33 ms at 120 Hz)** **[model]**; the only documented way below that is front-buffered rendering, which Google explicitly says is for small regions, not full-screen refresh **[verified]**. **No public high-speed-camera measurement of a Metal/Vulkan quad app on a current 120 Hz iPad or Android device was reachable from this sandbox**; the Stage-0 latency harness must establish the floor itself, and the gate should be written as "p95 ≤ measured-reference-quad + 1 frame", with the reference quad app shipped as part of the harness.
2. **Every API the shells need exists at OS versions we can require** (iOS 17 / Android 10 as the native floor, with graceful degradation to iOS 15 / API 26): `CAMetalDisplayLink` (iOS 17), `preferredFrameRateRange` (iOS 15), `maximumDrawableCount` = 2 (iOS 11.2), `presentsWithTransaction` (iOS 8), coalesced/predicted touches (iOS 9), Pencil hover `zOffset` (iPadOS 16.1), `MTLResidencySet` (iOS 18, Apple6+), `os_proc_available_memory` (iOS 13); `Choreographer.postVsyncCallback` with frame timelines (API 33), `Surface.setFrameRate` (API 30), `SurfaceControl` (API 29), `GLFrontBufferedRenderer` (API 29), `androidx.input:input-motionprediction:1.0.0` (stable 2025-11-19, minSdk 23), `AHardwareBuffer` (API 26), `ImageDecoder` hardware bitmaps (API 28). All **[verified]**.
3. **Hardware JPEG decode is not a lever on either platform.** Android's `BitmapFactory`/`ImageDecoder` decode through Skia's `SkCodec` → `jpeglib` **[verified in AOSP source]**, and the only hardware image codecs exposed by `MediaFormat` are HEIC and AVIF **[verified]**. Apple documents no hardware JPEG path in ImageIO **[verified by absence]**. Plan on libjpeg-turbo (NEON) in a thread pool on both, exactly as note 11-gap-2 §4.3 already prescribes; the native win over the web is zero-copy upload and threads, not a decoder.
4. **Texture upload is not the bottleneck natively.** Apple silicon is unified memory: a `storageModeShared` 2D-array texture accepts `replace(region:slice:)` CPU writes with no GPU copy **[verified]**; Android `AHardwareBuffer` is zero-copy into EGL/Vulkan and is exactly how HWUI uploads hardware bitmaps **[verified in AOSP source]**. A full-viewport refresh (≈20 × 1 MiB RGBA tiles) is a ~20 MiB memcpy, ≈ 2–4 ms of one CPU core **[estimate]**, which fits in one 8.3 ms interval if done off the render thread. Budget: **≤ 8 MiB/frame on phones, ≤ 32 MiB/frame on iPad Pro/M-series** **[estimate, to be measured with `gpuStartTime/gpuEndTime` and Vulkan timestamp queries]**.
5. **wgpu is adequate for the viewport on both platforms, but four seams must be kept replaceable**: (i) surface configuration (wgpu maps `desired_maximum_frame_latency` 1..2 to `maximumDrawableCount` 2..3 and honours a pre-set `presentsWithTransaction` **[verified in wgpu-hal source]**, but exposes no `present(afterMinimumDuration:)`, no `presentedTime` feedback — issue #9856 open — and no Vulkan frame-timeline/Swappy hook); (ii) texture allocation (no `MTLHeap`, purgeable state or residency-set control; no `AHardwareBuffer` import — `VK_ANDROID_external_memory_android_hardware_buffer` is not in wgpu's enabled-extension list **[verified by absence]**); (iii) the display-link/Choreographer loop (shell-owned anyway); (iv) input (shell-owned). Direct Metal is a cheap fallback for (i)–(ii) on iOS; direct Vulkan on Android is not worth it — MapLibre's 2026 changelog still adds Adreno 600 `VK_ERROR_DEVICE_LOST` workarounds **[verified]**, and wgpu/Firefox carry that burden for us.
6. **The real native risks are thermal and memory, not API availability.** Apple documents that 120 Hz is withdrawn in Low Power Mode, at critical thermal state and by the accessibility "Limit Frame Rate" toggle, and warns that adapting render quality to refresh rate can create a GPU-throttling feedback loop **[verified]**. iOS terminates apps above a device-dependent footprint limit with no published table **[verified that it is device-dependent; no table verified]**; Android's `isLowRamDevice` means "generally 1 GB or less" and 3–4 GB devices are not low-RAM, so our budget logic must use `MemoryInfo.availMem/threshold` and `onTrimMemory`, not the flag.

**Upload budget arithmetic [estimate]**: 512² RGBA8 tile = 1 MiB; 512² ASTC 4×4 = 256 KiB; 512² BC1 = 128 KiB (A17 Pro+ only). A phone viewport refresh of ~20 tiles (note 04 F5) is 20 MiB uncompressed. Single-core memcpy into a shared texture on A12–A18 class CPUs is in the 5–10 GB/s range **[estimate]**, so 20 MiB ≈ 2–4 ms CPU, done on an upload thread, not the render thread. GPU blits of 20 MiB are < 1 ms **[estimate]**. The constraint is therefore not bandwidth but *hazard tracking*: write only to array layers whose last GPU read was fenced (`MTLSharedEvent`/completion handlers), which the core's cache already models as "resident-but-not-visible" slots. 2048 layers × 1 MiB = 2 GiB per array; stay at ≤ 256 layers per array for parity with WebGPU/GLES 3.0 minimums (note 03 §2.7).

### 2.8 wgpu native behaviour that matters for the shells (read from v30 trunk sources)

- Metal surface: `PresentMode::Fifo` → `displaySyncEnabled = true`, `Immediate` → false, but `Immediate` is only advertised when `OsFeatures::display_sync()` (macOS) → **iOS gets Fifo only** **[verified]**. `maximum_frame_latency` range `1..=2` (iOS 11.2+) → `setMaximumDrawableCount(latency + 1)` → 2 or 3 drawables **[verified]**. `setAllowsNextDrawableTimeout(false)` always **[verified]**. `present()` uses `commandBuffer.presentDrawable` unless the layer's `presentsWithTransaction` is already true, in which case wgpu does `commit → waitUntilScheduled → drawable.present()` — i.e. the shell can configure the layer before handing it over and wgpu follows **[verified]**. ### 2.10 Tradespace: wgpu vs direct Metal/Vulkan for the native viewport

Scores 1 (poor) – 5 (best). "Direct" means hand-written Metal (Swift/ObjC or Rust via objc2) and Vulkan (Rust via ash) with the Rust core supplying decoded tiles and the draw list.

| Criterion (weight) | A. wgpu everywhere (shells own loop + input; wgpu owns surface, textures, shaders) | B. wgpu + `wgpu-hal`/`as_hal` escape hatches (shell creates `CAMetalLayer`/`MTLTexture`s with shared storage + purgeable state, `AHardwareBuffer`-backed `VkImage`s, imports them into wgpu) | C. Direct Metal on iOS, wgpu on Android | D. Direct Metal + direct Vulkan (+ GLES fallback written by us) |
|---|---|---|---|---|
| Present-path control (latency 1, drawable count, presentsWithTransaction, present(at:)/presentedTime, frame timelines, Swappy) (high) | 3 — latency 1 and drawable count yes; no presentedTime (#9856), no present(at:), no Vulkan frame-timeline/Swappy | 4 — Metal: full via raw layer/command queue; Android: still wgpu's swapchain | 5 iOS / 3 Android | 5 |
| Zero-copy upload (shared textures, AHardwareBuffer) (high) | 2 — staging copies via `write_texture`; no AHB import | 4 — raw `MTLTexture` import on Metal; AHB import needs a wgpu-hal patch **[unverified feasibility]** | 5 iOS / 2–4 Android | 5 |
| Memory control (heaps, purgeable, residency sets, device-loss recovery) (high) | 2 | 4 (Metal), 2 (Vulkan) | 5 / 2 | 5 |
| Driver-bug burden (Adreno/Mali/PowerVR/Xclipse) (high) | 5 — wgpu/naga/Firefox carry workarounds | 5 | 5 | 1 — MapLibre-style perpetual workaround work |
| Shader/pixel parity with web (WGSL→MSL/SPIR-V/GLSL by naga; golden images) (high) | 5 | 5 | 3 — second shader set (MSL) must be kept pixel-identical | 2 — three shader sets |
| GLES fallback for the ~15 % of devices without Vulkan or with broken Vulkan (med) | 5 — built in | 5 | 5 | 2 — ours to write |
| Effort to Stage-3 exit (med) | 1.0× | 1.2× | 1.6× | 2.5× **[estimate]** |
| Upstream churn risk (wgpu majors roughly quarterly; 28→30 in 8 months) (med) | 2 | 2 | 3 | 5 |
| Binary size per ABI (low) | wgpu + naga ≈ 3–6 MB release **[estimate]** | same | Metal path small; wgpu on Android same | smallest |
| Telemetry fidelity (GPU times, present times) (med) | 3 — timestamp queries only | 5 | 5 / 3 | 5 |

Weighted by Goal 1 (latency/no-blur) first and Goal 2 (platform reach) second, **B wins**: it keeps one renderer and one shader set, keeps the driver-bug burden upstream, and gives back the two levers that matter for latency and memory on iOS (raw layer config, shared/purgeable textures). C is the fallback if Stage-3 measurements on iPad miss the gate and profiling shows the loss is in wgpu's present/upload path rather than in our scheduler. D is rejected: MapLibre's 2026 changelog is the cost evidence.

## 3. Implications for our viewer

- **Goal 1 on iPad is bounded by 2 display intervals, not by anything we write.** Everything above the floor is ours: decode scheduling, upload hazards, and the frame-rate request. The native shell's job is to (a) run the core's fixed-timestep camera inside a `CAMetalDisplayLink` callback with `preferredFrameLatency = 1`, (b) request `CAFrameRateRange(80,120,120)` only while a gesture or inertial animation is live and fall back to `.default` when idle (Apple's "use sparingly" and the GPU-throttle warning), (c) feed the core `predictedTouches` as a *camera* input (pan/zoom target), never as tile requests — tile prefetch already uses the core's own velocity prediction (note 04 F3), and system prediction overshoot would waste bandwidth.
- **No-blur on native is still a scheduling problem.** Decode is libjpeg-turbo on both platforms (no hardware codec exists for us); a 20-tile viewport is 10–25 ms wall even on A-series big cores **[estimate]**. The native advantages are threads (no worker-message hop), zero-copy upload and GB-class caches; the LOD/fallback/prefetch rules from note 04 stay identical, which is what makes "one core, same behaviour" true.
- **Android's floor is one interval worse than iPad's** because of SurfaceFlinger. Mitigations that are documented and cheap: `SurfaceView` not `TextureView`; `postVsyncCallback` and render to the *preferred* timeline (never the earliest, which risks buffer-stuffing); `setFrameRate(120, DEFAULT, ONLY_IF_SEAMLESS)` during gestures; two-image swapchain (`desired_maximum_frame_latency = 1`); `requestUnbufferedDispatch` during gestures; `MotionEventPredictor` for the camera target. Front-buffered rendering is for the stylus *annotation ink overlay* (small region) and must not be used for the tile viewport.
- **Memory budgets become dynamic, not a table.** iOS: budget = f(`os_proc_available_memory()`) re-read after every `didReceiveMemoryWarning`, with the LRU tail of the GPU cache set `volatile` so it does not count toward the limit; `recommendedMaxWorkingSetSize` caps the resident set. Android: budget = min(k₁·`availMem`, k₂·`totalMem`) with `onTrimMemory` levels shrinking it, independent of `isLowRamDevice` (which is false on every 3–4 GB phone). Suggested starting constants **[estimate]**: GPU tile cache 1–2 GiB on 8–16 GB iPads, 512 MiB–1 GiB on 4–6 GB iPhones, 256–384 MiB on 3–4 GB Android, 96–128 MiB on Go/≤2 GB; decoded-CPU cache ≤ 25 % of that; encoded on-disk cache unbounded by RAM.
- **Texture-array design stays at ≤ 256 layers × 512² per array** (GLES 3.0 / WebGPU default minimum) even though Metal allows 2048; use several arrays. ASTC 4×4 (8 bpp) is the only compressed format available on every Apple GPU and most Android GPUs; BC is A17 Pro+/desktop only — compressed caching is therefore ASTC-or-nothing on mobile, and transcoding JPEG→ASTC in real time is not free; keep RGBA8 as the default and treat ASTC as a Stage-3 experiment.
- **wgpu stays, with escape hatches**: the shell constructs the `CAMetalLayer` (so wgpu does not add a sublayer and #3190 is avoided), sets `maximumDrawableCount`, `presentsWithTransaction` and `framebufferOnly` before handing it to wgpu; tile textures are created through `wgpu-hal` on Metal to get `shared` storage, `allowGPUOptimizedContents = false` and `setPurgeableState`. On Android, AHB import is the one hole: until a wgpu-hal patch exists, upload via `write_texture` from the decode thread (one extra copy, ~1 MiB per tile).

## 4. Recommendations

1. **Rewrite the latency claim and the Stage-3 gate.** Note 06 §2.3/§2.4 and §4.2: "iPad native: floor 2 frames (16.7 ms), typical 3; Android native: floor 3, typical 4, both at 120 Hz **[model, to be measured]**". Gate: "p95 input-to-photon ≤ reference-quad p95 + 1 interval; reference quad measured on the same device/firmware with the note-04 F8 rig". Ship the reference quad apps (raw Metal; raw Vulkan + SurfaceView) inside the Stage-0 harness repo.
2. **Minimum OS targets for the native shells**: iOS/iPadOS 17 (for `CAMetalDisplayLink`; `CADisplayLink` + `preferredFrameRateRange` fallback keeps iOS 15–16 working), Android 10 / API 29 (SurfaceControl, front-buffer library, Vulkan 1.1 on all 64-bit devices), with `postVsyncCallback` frame timelines used when API ≥ 33 and `Surface.setFrameRate` when API ≥ 30. Require `MTLGPUFamily.apple5` (A12) or later for the Metal path.
3. **Adopt option B** (wgpu + wgpu-hal escape hatches). Put the present path and the tile-texture allocator behind two small traits in the core (`PresentSink`, `TileTextureStore`) so a direct-Metal implementation can be swapped in without touching the scheduler. Decide at Stage-3 month 3 based on measured p95.
4. **Upload budget**: ≤ 8 MiB (8 tiles) per interval on phones, ≤ 32 MiB on iPad Pro/M-series, uploaded from decode threads into fenced array layers; measure per device with `gpuStartTime/gpuEndTime` and Vulkan timestamp queries, and adapt the budget online exactly as note 04 F5 proposes for the web.
5. **Frame-rate policy**: request 120 Hz only during gesture/inertia; drop to default when idle; never change render quality based on the granted rate (Apple's oscillation warning); read `CADisplayLink.targetTimestamp - timestamp` / `FrameTimeline.deadline` to detect downclocks and surface them in telemetry as a thermal event, not a frame drop.
6. **Decode**: libjpeg-turbo (NEON) via the `turbojpeg` crate on both shells, same source as the WASM build; thread pool sized to `activeProcessorCount - 1` on iOS and `availableProcessors() - 1` on Android, QoS/priority lowered for prefetch. Do not build an ImageIO or `ImageDecoder` path except behind the non-diagnostic flag from note 11-gap-2 §4.3.
7. **Input**: iOS — consume `coalescedTouches` for annotation ink, `predictedTouches` for the camera target only, `UIHoverGestureRecognizer(zOffset)` for a hover loupe on M2+ iPad Pro, `UIPencilInteraction` squeeze/double-tap for tool switching, `estimationUpdateIndex` plumbing for pressure. Android — `MotionEvent` history for ink, `MotionEventPredictor` for the camera target, `requestUnbufferedDispatch` during gestures, `FLAG_CANCELED` handling for palm rejection.
8. **Memory**: implement the dynamic budget above; on iOS add the increased-memory-limit entitlement (it only applies on some devices; behaviour must not depend on it); mark LRU-tail Metal textures `volatile`; on Android honour `onTrimMemory(TRIM_MEMORY_RUNNING_LOW/CRITICAL)` by halving the GPU cache; test the eviction logic against the per-tier table in note 06 §4.3 with a memory-pressure harness (iOS: allocate-until-warning tool; Android: `am send-trim-memory`).
9. **Driver-bug policy**: keep a device allow/deny list in the core (vendor/renderer string → backend preference: Vulkan, GLES, or "web only"); default Android backend Vulkan with automatic GLES retry on device creation failure or `VK_ERROR_DEVICE_LOST` in the first N frames (MapLibre's recovery behaviour); ship the GLES build always; run the golden-image suite on Adreno 6xx, Mali-G5x/G7x, Xclipse and a PowerVR device before each wgpu major bump, and pin wgpu to one major per release train.
10. **Packaging**: iOS `XCFramework` (device + simulator slices) with UniFFI Swift bindings, distributed by SwiftPM `binaryTarget` as Mozilla does; Android AAR built with `cargo ndk` for `arm64-v8a` + `armeabi-v7a` (+ `x86_64` for emulators), UniFFI Kotlin + JNA 5.12+; `rust-mobile/xbuild` only for the reference apps, not for the SDKs.

## 5. Open questions

1. **Measured floor.** No photodiode or high-speed-camera input-to-photon figure for a Metal/Vulkan quad app on a current iPad Pro or 120 Hz Android device was reachable; the model in §2.9 must be validated in Stage 0 (owner: harness). Dan Luu's table and Apple/Samsung marketing numbers are **[unverified]** here.
2. **Does UIKit deliver touch events at 120 Hz on ProMotion?** Apple's text says "around 60 Hz"; if delivery is per display frame at 120 Hz the sampling term in the model halves.
3. **iOS per-device footprint limits** by RAM class — needed to pre-size the cache before the first `os_proc_available_memory()` reading settles; measure with an allocate-until-warning tool on iPad (3 GB, 8 GB, 16 GB classes) and iPhone (4/6/8 GB).
4. **Can wgpu-hal import an `AHardwareBuffer`-backed `VkImage`** without an upstream patch (`texture_from_raw` + externally allocated memory)? If not, is the extra 1 MiB copy per tile measurable against the 8.3 ms budget on Mali-G52/Adreno 610?
5. **wgpu presentation feedback** (#9856) — needed for the telemetry schema; interim is `wgpu-hal` access to the `MTLDrawable` on Metal and `VK_GOOGLE_display_timing` / `VK_EXT_present_timing` availability on Android drivers **[unverified]**.
6. **Swappy compatibility**: Swappy wraps `vkQueuePresentKHR`/`eglSwapBuffers`; wgpu owns presentation, so Swappy is usable only via wgpu-hal. Decide whether the preferred-timeline Choreographer path is sufficient without Swappy.
7. **Android system motion prediction for finger (non-stylus) input** on Android 14+ — Google says it "may be limited to stylus events"; the Kalman fallback quality for pinch-zoom should be evaluated.
8. **ASTC transcode cost** (JPEG → ASTC 4×4 on CPU) vs RGBA8 memory — only worth it if the 3–4 GB Android budget proves too small for the no-blur prefetch radius.
9. **lmkd thresholds on 3–4 GB devices** and whether a foreground app with ~400 MiB of GPU-shared memory is ever killed in practice — source.android.com was unreachable; measure with `dumpsys meminfo` during soak tests.
10. **Hover on non-Pro iPads**: whether Pencil Pro/USB-C hover reports `zOffset` on iPad Air M2/M3 and iPad mini A17 Pro — not covered by the Apple sample's device list.
