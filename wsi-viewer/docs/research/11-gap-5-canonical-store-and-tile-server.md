# 11 — Gap 5: Feasibility of the canonical store (OME-Zarr v3 sharded with image-codec chunks) and build-vs-adopt for the tile server / edge translator

Research note for the Stoipath WSI viewer. Date: 2026-10-24. Inputs: notes 01, 02, 05, 07, 08 and the five architecture proposals (A–E). Method: primary sources fetched today from raw.githubusercontent.com (spec repos, READMEs, changelogs, source files), PyPI/npm/crates.io registry JSON, and web search where vendor sites were unreachable through the proxy. Labels: **[verified]** = read today from the cited primary source; **[snippet]** = taken from a search-engine excerpt of the cited page (page itself unreachable); **[unverified]** = could not be checked; **[reasoning]** = our inference. Raw downloads are kept under `../raw11/` for audit.

## Summary

1. **No image codec is registered for Zarr v3.** The normative registry (`zarr-developers/zarr-extensions/codecs`) lists 17 codecs today, none of them JPEG/J2K/HTJ2K/JXL/AVIF/WebP/PNG **[verified]**. The only production implementation of JPEG/HTJ2K/JXL chunks for Zarr v3 is `imagecodecs` 2026.10.10 (`imagecodecs/zarr.py`, names `imagecodecs_jpeg`, `imagecodecs_htj2k`, `imagecodecs_jpegxl`, …), which must be registered by an explicit `imagecodecs.zarr.register_codecs()` call and uses *unregistered raw names*, which ZEP 9 does not permit **[verified]**. zarrs, zarrita.js, tensorstore, Viv, vizarr, zarr-java/bioformats2raw and QuPath have no JPEG chunk codec **[verified]**. Storing brightfield as JPEG chunks in Zarr therefore produces a store that **only our own code can decode**; every third-party reader fails on the unknown codec name, and the standards credibility we wanted from "OME-Zarr canonical" is not delivered for brightfield.
2. **Zarr v3 sharding itself is fine.** Reading `sharding_indexed` is implemented in zarr-python 3.4.1, zarrs 0.23.14, zarrita 0.7.5 (since 0.0.2; crc32c-less index fixed in 0.7.5), tensorstore 0.1.85, zarr-java, Viv 0.23.0 (zarrita ^0.5.4) and vizarr 0.3.0 (zarrita ~0.6.0) **[verified]**. The pathology-desktop exception is **QuPath 0.7.0, whose OME-Zarr reader (Bio-Formats 8.4.0 + OMEZarrReader) still depends on jzarr 0.4.2, a Zarr v2 library** — QuPath cannot open any OME-Zarr 0.5 today, sharded or not **[verified pom.xml; QuPath-side inference]**.
3. **OME-NGFF 0.6 is released** (version_history.md: "0.6 - 2026-09-14", RFC-5 coordinate systems/transformations and `scene` adopted; 0.6rc0 was 2026-07-01) **[verified]**. 0.5/0.6 adoption in the *pathology* toolchain is real only on the Python side (ome-zarr-py 0.21.0 requires zarr>=3; napari-ome-zarr 0.11.0; bioformats2raw ≥0.12 writes `--ngff-version 0.5` via zarr-java) and the web side (Viv/vizarr). The NGFF spec says any Zarr codec "MAY be used … unless explicitly disallowed" and contains **no guidance on lossy image codecs** **[verified]**.
4. **DICOM WSI as the brightfield canonical is feasible today with open tooling:** wsidicomizer 0.31.0 writes TILED_FULL with `--format jpeg|jpeg2000|htjpeg2000|jpegxl`, `--offset-table basic|extended|empty`, `--add-missing-levels`, and (since 0.30.0, 2026-08-17) `--concatenate-frames/--concatenate-bytes` for the >4 GB case **[verified]**. Google Healthcare API and AWS HealthImaging return frames in the stored syntax on request (`transfer-syntax=*`; HealthImaging never transcodes on read and since Nov-2024 stores lossy JPEG/J2K/HTJ2K unchanged) **[snippet]**; dcm4chee's behaviour is reported inconsistent and the thread is unanswered **[verified discussion]**. Managed-store pricing is not the issue (Google: $0.39 per 100k frame retrievals); latency is (Google's own proxy quotes ~150 ms/frame) **[verified README]**.
5. **Recommendation (container):** *dual-standard, single-copy*. Brightfield 8-bit RGB → **DICOM WSI (TILED_FULL, JPEG-baseline frames copied from the vendor file, HTJ2K where >8-bit, Extended Offset Table, one instance per level, concatenation above 4 GB)**. Multichannel/16-bit → **OME-Zarr 0.5 (Zarr v3, `sharding_indexed`, 512² inner chunks, core `zstd`/`bytes` codecs only)**. Both served through one Rust translator over a single `TileIndex → (object, offset, length)` manifest. This is proposal C's storage stance and it is the only arrangement in which every pixel is stored once *and* every copy is readable by its community's standard tools. Zarr-with-JPEG-chunks stays an experiment behind a feature flag until a `jpeg`/`htj2k` codec is registered and implemented in at least zarr-python, zarrs and zarrita (an upstream programme we should run). Failure conditions are listed in F6.
6. **Recommendation (tile server): build in Rust, adopt libraries, do not fork a server.** No surveyed server (Iris RESTful, Google DICOM proxy, Orthanc WSI, large_image, IIPImage, Cantaloupe, Microsoft dicom-server (archived)) serves Zarr shards *and* DICOM frames by byte passthrough with bundles; Iris is the only one with published p50 ≈ 21 ms at 5k req/s, and it only serves its own IFE format **[verified]**. Crates: zarrs 0.23.14, dicom-object/pixeldata 0.10.0, tiff 0.11.3, turbojpeg 1.5.1, jpegxl-rs 0.16, axum 0.8.9 / hyper 1.12.0 / tower-http 0.7.1, moka 0.12.16 or foyer 0.22.6, object_store 0.14.2 or opendal 0.59.5, worker (workers-rs) 0.8.7. HTTP/3 in Rust is still `h3` 0.0.8 (May 2025) — terminate HTTP/3 at the CDN/Caddy, not in our process **[verified crates.io]**.
7. **Edge feasibility:** Cloudflare Workers (128 MB, 30 s CPU default on Paid, 10,000 subrequests, 6 simultaneous connections, R2 `get(..., {range})`) can host the translator; Cloudflare aligns origin range fetches to **1 MiB** boundaries, so shards should be 1 MiB-aligned **[verified docs]**. CloudFront Functions cannot (2 MB memory, 10 KB code, no network) and Lambda@Edge has no Rust runtime, so on AWS the translator is a regional origin service behind CloudFront **[snippet + reasoning]**.

## Findings

### F1. Image codecs as Zarr v3 codecs

**Registry.** `zarr-extensions/codecs` contains exactly: bitround, blosc, bytes, cast_value, conditional, crc32c, gzip, n5_default, packbits, reshape, scale_offset, sharding_indexed, transpose, vlen-bytes, vlen-utf8, zfp, zstd **[verified 2026-10-24]**. ZEP 9 ("Zarr Extension Naming", still under `draft/` in zarr-developers/zeps) requires that *raw* names (regex `^[a-z0-9-_.]+$`) be assigned in that repository, while *URI* names (`https://…`) may be used without coordination **[verified]**. Consequence: `imagecodecs_jpeg` is a raw name that is not registered, i.e. formally non-conformant; a conformant private codec today would be named like `https://stoipath.dev/zarr/codecs/jpeg`.

**What breaks if we store JPEG chunks in Zarr v3 today.** Any reader that does not have our codec class registered raises on the unknown `name` (zarr-python `KeyError`/`ValueError` from the registry; zarrita `Codec "…" not found`; zarrs "unsupported codec"; tensorstore schema validation error) — i.e. **vizarr, Viv, napari (default), QuPath (fails earlier on v3), tensorstore, zarrs_tools, bioformats2raw/raw2ometiff, OMERO, webKnossos all fail** on the brightfield arrays. The lossless fluorescence arrays (core codecs) remain readable by all of them. The metadata is still a valid OME-Zarr 0.5 hierarchy, so a reader that only needs thumbnails or the lossless channels could be pointed at a lossless low-resolution level, but no reader implements that fallback.

**Fallbacks.** (a) *Serve-through-translator only*: the Zarr store is private and all third parties get DICOMweb/IIIF/DZI views — honest but it means "OME-Zarr canonical" buys no interoperability for brightfield. (b) *Dual arrays* (lossless `zstd` RGB + JPEG delivery): a 100k² RGB slide is 30 GB raw and ~10–15 GB zstd (H&E compresses poorly losslessly) against ~3–4 GB JPEG — a 4–5x storage multiplier for the asset that is >90% of pathology volume; rejected. (c) *Register and implement the codec upstream* (F9) — 12–24 months before QuPath-class tools benefit, because QuPath first needs Zarr v3 at all.

### F2. OME-NGFF status

- **0.6 released 2026-09-14** with RFC-5 (coordinate systems, transformations, `scene`, `projectAxis`); breaking changes vs 0.6.devN (`input`/`output` must be `{name, path}` objects; `version` removed from `multiscales`, `plate`, `well`, `labels`) **[verified version_history.md; tag `0.6` exists in ome/ngff-spec]**. The RFC-5 document in `ome/ngff` main still carries `manual_status: S3` while RFC-2 (Zarr v3) is `S4` — status metadata lags the spec release **[verified]**.
- **Pathology toolchain adoption of 0.5/0.6:** Python (ome-zarr-py 0.21.0, napari-ome-zarr 0.11.0, ngff-zarr 0.50.0 — the latter advertises v0.6 read/write **[snippet]**), web (Viv 0.23.0, vizarr 0.3.0, zarrita 0.7.5), converters (bioformats2raw ≥0.12 via zarr-java; `--compression` for v3/0.5 limited to null/blosc/gzip/zstd; no sharding option documented in the README **[verified absence in README]**). **Not** QuPath 0.7.0 (jzarr), **not** Bio-Formats readers generally (OMEZarrReader → jzarr) **[verified]**. So "0.5 adoption in pathology" is real for research-Python and browser viewers and absent for the dominant desktop tool.
- **Lossy codecs:** the 0.6 text's only codec statement is "All features of the Zarr format including codecs … MAY be used with OME-Zarr unless explicitly disallowed in this specification" **[verified index.md]**. There is no `multiscales`-level guidance on lossy codecs, per-level codec choice, colour space, or ICC. Neuroglancer precomputed is the only sharded-store precedent with normative JPEG chunk text (chunk = 1- or 3-channel JPEG, width×height = chunk x × (y·z)) **[verified volume.md]**.

### F3. DICOM WSI as canonical: tooling, limits, server behaviour

**Writing.** wsidicomizer 0.31.0 (2026-09-28): sources opentile/tiffslide/openslide/czi/isyntax/bioformats; JPEG tiles from SVS/NDPI/Philips-TIFF are copied without re-encoding (NDPI via opentile's DCT-domain re-mux); `--format [jpeg|jpeg2000|htjpeg2000|jpegxl]` for re-encode; `--offset-table [basic|extended|empty]`; `--add-missing-levels`; concatenation via `--concatenate-frames`/`--concatenate-bytes` (0.30.0, 2026-08-17) **[verified README/CHANGELOG]**. wsidicom 0.36.1 reads JPEGBaseline8Bit, JPEG2000(+Lossless), HTJ2K, HTJ2KLossless, HTJ2KLosslessRPCL natively, more with imagecodecs; its `save()` writes fully tiled, BOT/EOT/no-OT, **never concatenated** **[verified]**. highdicom 0.28.2 exists for SEG/ANN/SR; its encoder transfer-syntax list was not verifiable today **[unverified]**. dicom-rs 0.10.0 (`dicom-transcode`) encodes JPEG baseline, JPEG-LS, JPEG XL lossless/lossy; HTJ2K encoding is not listed **[verified README]** — a Rust TILED_FULL writer with EOT would be our own code on top of `dicom-object`.

**4 GB and offset tables.** Encapsulated Pixel Data uses 32-bit fragment lengths and a 32-bit Basic Offset Table, so a level whose compressed frames exceed 4 GB cannot be addressed by a BOT; the 64-bit Extended Offset Table (0x7FE0,0001/0002) or a Concatenation (splitting a level across SOP instances with Concatenation UID/In-concatenation Number) is required, and archive support for both is uneven **[reasoning from PS3.5; CP number unverified]**. At JPEG q85 a 100k² base level is ~3–4 GB, i.e. right at the edge; the ingest must decide per level between EOT-only and concatenation, and wsidicomizer now offers both. A TILED_FULL instance with EOT is a range-addressable tile archive (frame i → EOT[i] offset/length), equivalent to a Zarr shard index but one table per level (51k frames × 16 B ≈ 0.8 MB) rather than one 1 KB index per 8×8 shard.

### F4. PMTiles-style internal archive (third option)

PMTiles v3: 127-byte header; root directory must fit in the first 16,384 bytes; optional leaf directories; `clustered` flag means tile data ordered by TileID (Hilbert) so neighbouring tiles are contiguous; run-length entries dedupe identical tiles; one HTTP range per tile after the directory is cached **[verified spec]**. It is the best *delivery* layout in the survey and the `pmtiles` JS client (4.5.0) is mature, but it has no pixel-type/colour/ICC/multichannel model, no bio ecosystem, and is read-only. Role: an optional *derived* offline/edge bundle (one file per slide for iPad/desktop downloads), never canonical.

**Recommendation: B.** It is the only row with no `−−`. Explicit failure conditions that would flip the decision:

1. **To A (Zarr for everything):** a `jpeg`/`htj2k` codec is registered in zarr-extensions *and* shipped in zarr-python, zarrs and zarrita *and* QuPath reads Zarr v3 — then brightfield OME-Zarr becomes readable by the toolchain and the single-container simplification is worth a migration (our translator makes the migration a background job).
2. **To D (DICOM for everything):** if early customers are >90% clinical, fluorescence stays <5% of slides, and DICOM 16-bit optical-path tooling (wsidicomizer/highdicom) proves adequate — then the Zarr side is not worth its own code path in v1.
3. **To C/F (accept a second copy):** if a regulator or customer VNA demands DICOM files *and* a research group demands OME-Zarr brightfield; then the export is a cost line, not an architecture change.
4. **B itself fails** if (i) the DICOM EOT/concatenation handling turns out to break common VNAs for >4 GB levels (then split levels into ≤2 GB instances at ingest), or (ii) the prototype shows per-level EOT loading makes client-direct range reads (desktop/Python) slower than the Zarr index path by more than one RTT at slide open — fixable by publishing our ≤100 KB manifest alongside.

### F7. Shard geometry evidence

No published measurement compares 8×8 with 16×16 inner chunks per shard for a CDN; what exists is design guidance:

- zarr-python performance guide: "The chunk shape determines what unit of your data can be read independently, while the shard shape determines what unit of your data can be written efficiently"; default within-shard order is Morton (`subchunk_write_order` = morton | lexicographic | colexicographic | unordered) **[verified]**.
- ZEP 2 worked example: 32³ chunks per shard; Zarr-vectors spec suggests 10–100 MB per shard and names the Neuroglancer-style 8×8×8 (512 inner chunks) default, with the trade-off "if most reads fetch entire shards, larger shards save requests; if reads touch one or two inner chunks, smaller shards waste fewer range-request bytes" **[snippet]**.
- Neuroglancer: sharding adds "somewhat higher read latency due to the need to retrieve additional index information … partially mitigated by client-side caching of the index data" **[verified sharded.md]**.
- Cloudflare: origin range fetches are 1 MiB-aligned; a 1 KiB client range can cost a 1 MiB origin read **[verified]**. CloudFront "may request a larger range than the client requested" **[verified]**.
- PMTiles: root directory ≤16 KiB so one request opens the archive **[verified]**.

**[reasoning] applied to our grid** (512² JPEG q85 ≈ 60 KB/tile):

| Geometry | Shard size | Index size | Shards per 100k² base level | 1080p viewport (15 tiles) touches | Lazy-tiler write-through unit | CDN 1 MiB slices per shard |
|---|---|---|---|---|---|---|
| 8×8 (4096² px) | ~3.8 MB | 64×16+4 = 1,028 B | ~600 | 1–4 shards → 1–4 index reads (cached) + 1–4 data ranges | 4 MB rewrite, or append + index rewrite | 4 |
| 16×16 (8192² px) | ~15 MB | 4,100 B | ~150 | 1–2 shards | 15 MB rewrite | 15 |

Because the CDN caches 1 MiB slices rather than whole shards, shard size barely affects hit rate; it affects index bytes per open (16× fewer indices at 16×16 but 4× larger), rewrite cost during lazy ingest (favouring 8×8), and object count (both trivial). 8×8 is the right default; make it a per-level parameter and measure. **Co-location of channels/z:** put all channels of a tile in one shard (shard shape `(c=all, y=4, x=4)` for ≤8 channels) so a channel-group bundle is one contiguous range, and keep z-planes in separate shards (focus scrolling prefetches z±1 as separate requests anyway); single-channel reads then pay sparse ranges within the shard, which the 1 MiB CDN slice absorbs for 4–8 channels of 512² uint16 zstd (~100–250 KB per channel-tile). Only a prototype can confirm.

### F8. Upstream contributions the project would need to make

1. **zarr-extensions**: register `jpeg` (and `htj2k`, `jpegxl`) array→bytes codecs with a README/schema defining chunk layout (`(y, x, c)` interleaved 8-bit, 1 or 3 channels), colour space, optional shared quantisation tables, and `must_understand` semantics; reference data. Prerequisite for anything else and for ZEP 9 conformance.
2. **zarr-python**: upstream the imagecodecs-backed implementation under the registered name (or an entry-point package `zarr-codecs-image`) so `ome-zarr-py`/napari work without manual registration.
3. **zarrs**: a `jpeg` codec plugin (turbojpeg/zune-jpeg) — needed for our server anyway.
4. **zarrita.js**: a `jpeg` codec using `ImageDecoder`/`createImageBitmap` with a wasm fallback — needed for Viv/vizarr.
5. **OME-NGFF**: an RFC adding guidance for lossy codecs in `multiscales` (allowed codecs per level, ICC/colour-space metadata location, provenance flag for re-encoded vs passthrough tiles).
6. **Bio-Formats OMEZarrReader → zarr-java** (QuPath's blocker); without it no Zarr v3 reaches QuPath/OMERO.
7. **wsidicomizer**: Rust-speed is not upstreamable, but conformance fixtures (EOT, concatenation, HTJ2K, JXL) and a published TILED_FULL+EOT test corpus are.
8. **dicom-rs**: HTJ2K encode/decode via OpenJPH, if we build the writer there.

### F9. Open items only a prototype can settle

- Hot-path service time of the Rust translator for (a) Zarr shard range, (b) DICOM EOT frame, (c) 15-tile bundle — p99 ≤ 10 ms target on a 2-vCPU container and in a Worker.
- Cold-path S3/R2 first-byte for 1 MiB-aligned shard ranges vs per-tile objects.
- Whether per-level EOT loading (0.8 MB) at slide open is acceptable for client-direct range readers (desktop/Python) or whether the manifest must be published alongside.
- Real CDN hit rate by shard geometry under recorded pathologist navigation traces.
- Whether a lazy-tiler write-through into a shard (append + index rewrite) is safe under concurrent readers on S3/R2 (no atomic append; use write-new-object + manifest pointer swap).
- Browser decode of HTJ2K chunks from DICOM frames on low-end Android (openjphjs/@cornerstonejs/codec-openjph 2.4.11) — decides whether HTJ2K frames can be served to browsers directly or must be transcoded to JPEG at the translator.

## Implications for our viewer

1. **The client never needs a Zarr JPEG codec.** Browsers and native SDKs fetch tiles from the translator (immutable URLs, bundles) or read standards directly (WADO-RS frames; OME-Zarr core codecs via zarrita/zarrs). Only desktop/Python power users who want raw container access read our stores directly, and both stores are standards for their pixel types.
2. **One manifest abstraction, two containers.** `TileIndex(level, x, y, c, z) → (object, offset, length, codec, provenance)` built at ingest and cached at the edge; Zarr shard indices and DICOM EOTs are just two sources for it (proposal C's design). The DICOMweb façade over the Zarr side and the IIIF/DZI façades over both are stateless translations.
3. **Instant zoom is unaffected by the container choice**, because both are byte-passthrough with a small index; what matters is 512² tiles, 1 MiB-aligned layout, centre-of-viewport bundling, and the hot cache. The decision is about interoperability and ingest cost, not latency.
4. **QuPath interoperability goes through DICOM (and OME-TIFF export), not OME-Zarr**, until Bio-Formats moves to zarr-java.
5. **Hosting choice is unchanged** (note 02 R7): Cloudflare R2 + Workers first-class; AWS with a regional origin; on-prem same binary.
