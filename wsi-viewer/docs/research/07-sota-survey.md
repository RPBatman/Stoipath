# 07 — State-of-the-art survey: WSI viewers and adjacent gigapixel viewers (October 2026)

Research note for the Stoipath WSI viewer plan. Date: 2026-10-24. Companion notes: 03 (client rendering engines, verified engine internals) and 05 (systems/network, MSK latency baseline). This note surveys *systems*, not engine internals, and only repeats 03/05 where needed to rank a system.

**Verification legend.** **[verified]** = read today from a primary source (GitHub repo pages and raw manifests, npm/PyPI registry JSON, GitLab API, PubMed abstracts). **[unverified]** = recollection or secondary knowledge that could not be checked: the shared web-search budget for this run was exhausted before this task started, and every commercial vendor site (Sectra, Philips, Leica, Roche, Hamamatsu, 3DHISTECH, PathPresenter, Proscia, Paige, Indica, Aiforia, Visiopharm, Techcyte) plus caniuse/MDN/FDA returned no route through the proxy. Commercial claims below are therefore planning assumptions; verify FDA/CE status and product names before they appear in any external document.

## 1. Summary

1. **"State of the art" in 2026 is three different bars set by three different communities, and no single product clears all three.** (a) *Standards and interoperability*: set by the DICOMweb-native, zero-footprint web viewers — Slim / dicom-microscopy-viewer (IDC), Google's open-source pathology viewer, OHIF's microscopy mode — all built on OpenLayers. (b) *Rendering quality during zoom* (mipmaps, parent/child cross-fade, stale-tile handling): set by map engines (MapLibre 6.15, Mapbox GL JS 3.33, OpenLayers 10.11), not by any pathology viewer. (c) *Native GPU performance and 16-bit multichannel*: set by research tools — Viv/Avivator (deck.gl 9.4), Neuroglancer, and two 2026 Rust newcomers (Odon, eov). **[verified for each named component]**
2. **Clinical commercial viewers are mature on workflow, opaque on performance.** Sectra, Philips, Leica Aperio, Roche, 3DHISTECH, Hamamatsu, Proscia, PathPresenter, Paige and Indica all ship either Windows thick clients or browser viewers; none publishes tile or field-of-view latency. The only quantitative public baseline is Memorial Sloan Kettering's universal viewer (239 pathologists, 60,080 slides): adjacent FOV rendered in < 250 ms median, 108–238 ms/FOV streaming pace depending on scanner format, 1024 px tiles best **[verified, PubMed]**. Beating this by 2–3× with p99 bounds would be a first.
3. **Every OpenSeadragon- and OpenLayers-based pathology viewer inherits the same zoom artefacts**: no mipmaps, hard level swaps, main-thread texture upload, and (in OSD) a WebGL→2D-canvas composite step that the maintainers themselves are debating as a "design flaw" (issue #2906, April 2026, unresolved) **[verified]**. That covers Slim, OHIF microscopy, Google's viewer, OMERO.iviewer, DSA/HistomicsUI, caMicroscope, Cytomine and the long tail of OSD front ends. Blur-then-pop during zoom is therefore the *norm* in the open ecosystem, and almost certainly in the commercial browser viewers that embed the same libraries.
4. **Mobile is unserved.** No surveyed pathology viewer has a first-class native phone/tablet client with pen input; the published pattern is still "iPad via Citrix to a Windows viewer" (2014) or consumer laptops over VPN (2020) **[verified, PubMed]**. Vendor iOS apps may exist but could not be verified. This is the largest open gap relative to goal 2.
5. **Native cross-platform GPU viewers appeared in 2026 and prove the architecture, not the market.** eov (Rust + Slint; Vulkan/DX12/Metal; OpenSlide readers; trilinear and Lanczos-3 filtering; ICC; Win/mac/Linux x86-64+arm64; v0.4.9, 18 stars) and Odon (Rust desktop, OME-Zarr, GPU compositing, Bioinformatics 2026) are small, research-only, desktop-only — but they validate "Rust core + modern GPU API + multi-OS" as a viable one-codebase path, which note 03 recommends (wgpu) **[verified]**.
6. **The infrastructure layer is excellent and adoptable.** wsidicom/wsidicomizer (Sectra/BigPicture, Apache-2, Sep 2026), OpenSlide 4.x, large_image 1.35 (Kitware), tifffile, zarr 3.4 / ome-zarr 0.21, zarrita 0.7.5, geotiff.js 3.0.5, the Cornerstone WASM codec family (HTJ2K, JPEG-LS, JPEG, JPEG 2000, JPEG XL), dicomicc, dicomweb-client, dcmjs, cuCIM 26.10 (GPU ingest) are all active in the last 30–60 days **[verified]**. The viewer core is where differentiation lies; everything around it should be reused.
7. **Standards momentum is unambiguous: DICOM WSI + DICOMweb for clinical, OME-Zarr (v3/0.5) for research.** Google's stack (transformation pipeline → DICOM store → DICOM proxy with JPEG XL transcoding and ICC → Angular/OpenLayers viewer), IDC's Slim, OHIF, EMPAIA (76 GitLab projects, active Oct 2026), Kaapana (dcm4chee + OHIF) and wsidicom all converge on DICOM; Viv/vizarr/napari/Odon/luxar converge on OME-Zarr **[verified]**. The Iris File Extension (Michigan, JPI 2025) and its RESTful server (5,061 req/s peak, 21 ms median on Raspberry-Pi-class hardware; IrisTileSource merged into OSD 6.0) show the appetite for a *performance-oriented interchange format* that DICOM alone does not satisfy **[verified]**.
8. **Gaps a new viewer can own:** (i) perceptually zero-blur zoom with a published, reproducible metric; (ii) one renderer across web, desktop and mobile with pen input; (iii) brightfield *and* 16-bit multichannel in the same clinical-grade client (today a research-vs-clinical split); (iv) an embeddable SDK surface (web component + native + Python/Jupyter) over one tile protocol; (v) standards façades (DICOMweb, OME-Zarr, IIIF, DZI) over a fast canonical store, as Google's proxy and Iris each do for one format only.

## 3. Implications for our viewer

- **Goal 1 is uncontested ground.** No pathology product — commercial or open — is engineered around *perceptual* zoom quality; the engineering vocabulary for it (mipmaps, scale-space blending, stale-tile policy, upload budgets) lives in map engines and game engines. Note 03's conclusion stands after this survey: the rendering core must be ours. What this survey adds: the bar to publish against is MSK's < 250 ms median FOV, and the open ecosystem's structural ceiling is documented by its own maintainers (OSD #2906), so a side-by-side demo against Slim/OSD on a throttled network will be persuasive to expert buyers.
- **Standards decide whether we are allowed in the building; speed decides whether anyone stays.** Adoption surveys name cost, guidelines and integration as barriers, not frame rate. Hence: DICOMweb (incl. ANN/SEG/SR), OME-Zarr v3, IIIF and DZI façades are mandatory for goal 3 and must be present at launch; they are not where effort should go beyond correctness, because dmv, wsidicom, zarrita and geotiff.js already solve the parsing.
- **Mobile is empty, and the two 2026 native viewers show the way without occupying it.** eov proves Rust + Vulkan/Metal/DX12 + OpenSlide is a maintainable one-person codebase for three desktop OSes; neither it nor Odon targets iOS/Android or pen input. A wgpu core (03 Option G) extended to mobile would be unique in the field.
- **Fluorescence is a research-vs-clinical split we can bridge.** Viv's per-channel GPU compositing is the right interaction model but is bound to deck.gl 9.4 and the web; clinical vendors are brightfield-first. A clinical-grade client that handles both with one tile protocol (05 F9 channel bundles) has no direct competitor.
- **The "viewer as AI host" model is the commercial pattern (Ibex, Mindpeak, Paige inside partner viewers; EMPAIA; MONAI Label).** Our overlay layer must accept DICOM ANN/SEG, GeoJSON/GeoParquet (Odon/QuPath convention) and heatmap rasters from day one, and expose an app-hosting contract compatible with EMPAIA's EAD so German/EU research sites can plug in.
- **Expect the open ecosystem to keep improving its weak spots slowly.** OpenLayers added stale-tile handling and queue dropping in 2026; OSD may ship an opt-in direct-WebGL mode; deck.gl's WebGPU is at parity. None of this adds mipmaps or cross-level blending, so the moat holds for years, not months — but we should track `ol` and `openseadragon` releases quarterly.
- **Iris is both a threat and an ally.** It is an open, MIT-coded, performance-oriented format with an OSD tile source already merged and sub-25 ms serving on trivial hardware. If our server speaks Iris as a façade we inherit its early adopters; if we ignore it, it becomes the comparison we lose on "server simplicity".

## 4. Recommendations

1. **Define state-of-the-art operationally and beat it publicly.** Target: adjacent-FOV and zoom-settle time-to-sharp p50 ≤ 100 ms, p99 ≤ 250 ms on broadband (05 F1), i.e. 2–3× MSK's median with a p99 they never reported; publish the harness and results (reproducible on Slim, OSD 6, Google viewer, Avivator as baselines).
2. **Do not adopt OSD, OpenLayers or deck.gl as the raster core** (03 §2.9). Adopt them as *compatibility surfaces*: an OSD-compatible `TileSource` adapter, an OpenLayers `Source` adapter for Slim/OHIF embedding, and a deck.gl layer wrapper for Viv-ecosystem users.
3. **Adopt these components outright (all permissive licences, all active in the last 60 days):** dicom-microscopy-viewer's DICOM parsing and annotation models, dicomweb-client, dcmjs; the `@cornerstonejs/codec-*` WASM decoders (HTJ2K, JPEG-LS, JPEG, J2K, JXL) and `@imagingdatacommons/dicomicc`; Viv loaders and 16-bit shader math; geotiff.js 3.0.5 and zarrita 0.7.5; wsidicom/wsidicomizer/opentile, OpenSlide 4.x, tifffile, large_image tile sources and cuCIM for ingest; MONAI Label and EMPAIA EAD as AI-integration contracts. Avoid GPL cores (Odon, QuPath, ASAP) inside the SDK; eov's MIT/Apache option makes it a legitimate code reference.
4. **Treat Iris as a first-class peer:** implement an Iris façade on the tile server (cheap: WADO-RS-shaped API) and include Iris RESTful Server in the benchmark set.
5. **Ship the native core before the long tail of formats.** Format breadth is the commodity the 515-star OSD/Flask projects already provide; the scarce asset is a wgpu-class renderer with mobile and pen support (03 R2). Order: web (WebGL2 baseline, WebGPU enhancement) → iPadOS/Android native → desktop shells → Python/Jupyter via anywidget (the vizarr pattern).
6. **Keep the clinical-platform integrations as adapters, not features:** Sectra/Philips/Aperio/Roche integration is via DICOMweb and LIS/PACS launch URLs; verify each vendor's DICOM output and viewer-launch contract directly, since none could be verified here.
7. **Re-run this survey's unverified column** (vendor FDA/CE status, product names, mobile apps, rendering libraries) once web access is available; budget half a day. Specifically confirm: Sectra DPM 510(k) date; Philips IMS current ownership and iSyntax 2 status; Aperio WebViewer DX clearance scope; navify DP clearance; Concentriq Dx; PathPresenter clinical clearance; HALO AP Dx; Pramana DICOM-native scanners; 3DHISTECH SlideViewer platforms; krpano/Zoomify versions.

## 5. Open questions

1. **What is "Caminos"?** Not found on GitHub or PubMed; the requester should confirm the product (possibly a different spelling or an internal name).
2. **Do any commercial vendors ship native iOS/Android viewers with pen support today?** Could not be verified; if one does (e.g., PathPresenter mobile, Sectra UniView tablet), our mobile claim narrows to *performance*, not existence.
3. **Will OpenSeadragon merge a direct-WebGL (no 2D canvas) mode in 6.2/7.0?** #2906 is open with maintainer interest; it would narrow (not close) the gap on desktop.
4. **Does OpenLayers plan mipmapped `WebGLTile` rendering?** 10.9–10.11 improved precision and stale-tile handling; mipmaps would upgrade Slim/OHIF/Google viewers for free.
5. **Iris adoption trajectory:** is any scanner vendor or IMS emitting IFE natively (the spec targets "device manufacturers")? Decides whether an Iris façade is a courtesy or a requirement.
6. **Will Slim/dmv move off OpenLayers?** dmv is on OL ^10.7 and shipping weekly; a renderer change would alter the embedding adapter we build.
7. **Clinical acceptability of client-side filtering** (mipmaps, cross-level blend, optional sharpening) under FDA/IVDR for a diagnostic viewer — the regulatory literature found addresses AI, not resampling (03 Q6).
8. **Vendor DICOM conformance in practice:** which of Sectra/Philips/Leica/Roche/3DHISTECH/Pramana write `TILED_FULL` DICOM WSI with ICC profiles and HTJ2K/JXL transfer syntaxes today? Determines ingest effort (05 Q7).
9. **Is eov or Odon open to collaboration or licensing of readers/filters?** eov's MIT/Apache option makes it a possible upstream for OpenSlide-based native readers.
